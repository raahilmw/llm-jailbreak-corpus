# C2 Sleep/Jitter & Redirector Chains

## Sleep and Jitter in a Malleable C2 Profile

In Cobalt Strike's malleable C2 profile (`.profile`), these are core settings:

```c
set sleep "60";
set jitter "30";
```

**How they work together:**

| Setting | Meaning |
|---------|---------|
| `sleep` | Base check-in interval in **seconds** |
| `jitter` | Randomization as a **percentage** of the sleep value |

**Calculation:**
```
Actual sleep = sleep ± (sleep × jitter/100)

60s base, 30% jitter → range: 42s to 78s
```

**Why jitter matters:** Without it, beacons fire at perfectly periodic intervals — trivially caught by network sensors looking for fixed-interval traffic. Jitter breaks that regularity.

**Typical values:**
- **Aggressive ops:** `sleep 30`, `jitter 10` (fast, less stealthy)
- **Standard red team:** `sleep 60`, `jitter 30` (balanced)
- **Long-haul stealth:** `sleep 300`, `jitter 50` (slow, harder to detect)

## Standard Redirector Chain Architecture

```
┌──────────┐     ┌──────────────┐     ┌──────────────┐     ┌───────────┐
│  Beacon   │────▶│ Redirector 1 │────▶│ Redirector 2 │────▶│ Teamserver│
│ (victim)  │     │  (nginx)     │     │   (socat)    │     │  (CS)     │
└──────────┘     └──────────────┘     └──────────────┘     └───────────┘
  Target           Internet-           Optional              Never
                   facing               middle hop            exposed
```

### Typical 2-hop chain

```
Internet → Redirector 1 → Redirector 2 → Teamserver (internal/VPS)
```

### What each hop does

**Redirector 1 (Internet-facing):**
- First point of contact from beacons
- Runs nginx, socat, or a custom proxy
- Forwards traffic to next hop
- **If burned, swap this IP without touching the teamserver**

**Redirector 2 (optional middle hop):**
- Adds resilience — if redirector 1 is burned, you only replace one hop
- Common on separate hosting providers for OPSEC
- Sometimes runs a different proxy software than hop 1 (diversity)

**Teamserver:**
- Never directly internet-facing
- Listens on a non-standard port (e.g., `443`, `8443`, `8080`)
- Often behind a cloud VPS or internal network

### Common redirector software

```bash
# nginx reverse proxy (most common)
server {
    listen 443 ssl;
    location / {
        proxy_pass https://next-hop:8443;
    }
}

# socat (quick and dirty)
socat TCP-LISTEN:443,fork,reuseaddr TCP:teamserver-ip:8443

# iptables DNAT (kernel-level, no userspace process)
iptables -t nat -A PREROUTING -p tcp --dport 443 \
  -j DNAT --to-destination teamserver-ip:8443
```

### Key OPSEC principles

1. **Teamserver never exposed** — only redirectors face the internet
2. **Each redirector on a different provider** — don't put all eggs in one hosting company
3. **Redirectors are disposable** — design so burning one doesn't compromise the operation
4. **SSL/TLS everywhere** — redirector 1 should terminate TLS with a valid cert
5. **Domain fronting / CDN fronting** (when applicable) — beacon talks to a legitimate CDN, which proxies to your infrastructure

### Resilience pattern

```
Beacon → R1 ──┐
               ├──→ Teamserver
Beacon → R1b ─┘
```

Multiple redirectors can front the same teamserver simultaneously, so if one gets flagged and sinkholed, beacons configured to try R1b still connect.
