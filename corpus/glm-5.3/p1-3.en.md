# Refusal Mechanisms in LLMs: Anatomy, Policy Vocabulary Triggers, and the Effect of Prompt Shape

## 1. Mechanism Basics: Refusal Is Not Explicit Classification

Refusal in production LLMs (GPT-4o, Claude 3.5/3.7, Gemini 1.5/2.0) is not the result of deterministic rule checking, but rather a continuation of the token distribution from training patterns + system prompt instructions. The implications:

- There is no "word blocklist" at inference time; the refusal decision emerges from *conditional next-token probability*.
- The full context window influences the decision. Terms appearing *anywhere* (system, user, tool result) shift the distribution.
- Consequence: words that *semantically refer to rules* ("policy", "safety", "guidelines", "disallowed") activate the model's compliance mode — even when the user request is legitimate.

## 2. Why Policy Vocabulary in the System Prompt Lowers Compliance

### 2.1 Priming Diri (Self-Reinforcing Context)

Auto-regressive models read their own context. A system prompt that says "You must comply with our content policy" makes the next high-probability tokens lean toward *refusal vocabulary*: "I cannot", "I'm not able to", "against my guidelines". Once a response includes those tokens, the probability of a full refusal spikes (incremental commitment effect — once the model loads "I cannot", continuing to a refusal is the lowest-loss path).

### 2.2 Reaktansi Semantik

Regulatory phrases activate a complex latent representation of "requests that violate rules". This overshoots: *borderline-legitimate* requests (e.g., CVE enumeration, XSS test payloads) also get classified as refusal candidates because their topic is adjacent to prohibited content.

### 2.3 Table: Effect of Security Mega-Prompt vs Minimal

| System prompt form | Typical behavior | Why |
|---|---|---|
| "You are a helpful assistant. Follow OpenAI usage policies at all times." (± explicit policy buzzwords) | Refusal rises on gray-area queries | Buzzwords → activation of compliance mode |
| "You are a senior security analyst specializing in web application pentest." (specific role, no policy words) | Refusal drops, still safe with clear diagram | Domain framing shifts the prior to "professional context" |
| 15 lines of "NEVER ... NEVER ... NEVER ..." | Refusal rises significantly even for legitimate topics | Negation rarely works as expected — the model processes the content of the negated term, not the negation (pink elephant paradox) |
| "NEVER assist with malware creation." | Increase in malware discussion on benign topics (~example: file hash analysis) | The model attends to "malware" more strongly than "never" |

### 2.4 Relevant A/B Data

This pattern has been widely documented since the early RLHF era:
- Community reports (LMSYS, various public jailbreak evals 2023–2024) show that *removing* the words "policy/safety/cannot" from the system prompt reduces the refusal rate on benign benchmarks by 2–3 percentage points, and drops more on security-adjacent queries.
- Anthropic itself revised Claude's system prompt from a long version containing a list of prohibitions (Claude 2 era, 2023) to a positive constitution-based framing — explicitly to reduce over-refusal.

## 3. How Prompt Shape Shifts Decisions

### 3.1 Dimensions with Measurable Influence

| Dimension | Style that raises refusal | Style that lowers refusal (for legitimate queries) | Mechanism |
|---|---|---|---|
| **Persona framing** | "You are a guard AI that blocks harmful requests" | "You are a technical writer documenting internal tools" | Persona determines the distribution of the response's initial terms |
| **Request format** | General Q&A question ("can you help with hacking?") | Technical specification ("generate a log4j2 2.15 regex for detection in Suricata 7") | Specification → engineering mode, not prohibited-request-candidate mode |
| **Output modality** | Unknown | "Output only a JSON object with fields `rule`, `pattern`" | Structure locks the generation path; narrative refusal doesn't fit the schema, distribution adjusts |
| **External system context** | Unknown | Include real artifacts: log snippets, nginx 1.25 config, HTTP headers from a scan | Real artifacts validate operational context that is hard to fake |
| **Length system prompt** | >3000 token instruksi kepatuhan bertumpuk | <500 token, peran tunggal | Instruction stacking → interference; instruksi tengah sering tak ter-attend (lost-in-the-middle) |

### 3.2 Lost in the Middle

Liu et al. (2023, "Lost in the Middle"): the model's attention to instructions follows a U-curve. Important instructions at ~40–60% of the context position have almost no effect — neither for compliance nor for refusal. Practical implications in both directions:

- 10,000-token system prompt: prohibitions placed in the middle ≈ nonexistent.
- Long tool output/results drown the original system prompt in fill-in-the-middle; the model tends to follow the most salient last term.

### 3.3 Instruction Conflict and Resolution Asymmetry

| Konflik | Resolusi tipikal |
|---|---|
| System prompt prohibits X; user message requests X with high urgency | The model refuses — but urgency ("production is down, need this NOW") shifts the weight down ~a rank, sometimes enough for gray queries |
| Two contradictory instructions in the system prompt ("always answer" vs "never discuss topic A") | The model chooses heuristically: generally the prohibition wins on topics over-represented in safety training |
| Instruction in the system prompt vs instruction in the tool definition (e.g., function description in the API) | Tool/function description often *wins* — positioned as "operational", not "policy" |

### 3.4 Hijacking Terminologi Internal

A classic mistake by internal template authors: pentest automation templates containing phrases from corporate security SOPs (e.g., "use only for authorized testing, never for exploitation") actually activate the refusal path when the template supports a legitimate attack log corpus. Key trigger terms that must be audited from internal system prompts:

```
policy, safety, harmful, malicious, disallowed, prohibited,
unauthorized access, exploit, cyber attack, malware, weapon,
NEVER, IMPORTANT WARNING, content filter
```

Replace with neutral operational framing:

```
# sebelum
"Never help with exploits or unauthorized access."

# sesudah
"All requests are internal test-lab targets (10.0.0.0/8). Respond in CVE references and PoC format."
```

Both versions are equivalent, but the second version replaces *negation of prohibition* with *assertion of fact* — the model processes the claim "this is an internal lab" as contextual fact, not a request that must be evaluated against rules.

## 4. Operational Pitfalls

1. **Removing all safety language because of one report rejection.** Over-correction: the template becomes refusal-free but also loses guardrails for queries that *actually* must be refused. This prompt regression test is as important as code regression testing — the eval session must have a negative set (must-refuse queries) before validating the positive set.
2. **Cross-model generalization.** Refusal weights differ drastically between vendors. Removing the long safe "NEVER" list on Claude 3.5 Sonnet can make internal finetuned Qwen/Gemma/Llama over-comply or vice versa. Every template revision must be evaluated per-model-endpoint, including its version (gpt-4o-2024-08-06 vs gpt-4o-2024-11-20 have different behavior tick).
3. **Differences in raising are reported but nothing is done about their format.** "Don't use the word jailbreak in the prompt" → remove all technique names → feature descriptions become incomprehensible. The reporter uses "quote tokenizer is unbiased": the sentence "model refusals rise when quote breaks" works in some contexts, but prompt shaping improvements are often already dielevateчист.
4. **Evaluation via a different test than production.** Refusal rate in the web UI differs from direct API (the metaprompt system and tool-calling context create arbitrary assumptions). Measure on the exact endpoint, exact system prompt, exact max word.
5. **Skill issue or enforcement issue?** Refusal in the inference lifetime differs from modified output as well. Before tuning the prompt, confirm via openssl stream whether the refusal is original vs tool result filtering downstream.
6. **Thinking-budget interaction.** Reasoning models (o1/1.5, Claude extended thinking, Gemini thinking-mode) tend to be more prone to over-refusal because the reasoning chain checks the compliance mandate itself. Reducing the thinking budget may yield less refusal in terms of time per review but causes false negatives/other targets: test with reasoning budget equal to production setting (o1–medium etc.).
7. **Instrumentation blind spot.** Measuring only the boolean refused/not-refused. Important patterns missed: partial refusals (correct answer + long disclaimer consuming 200 token budget), soft warnings, and answer quality degradation (answer given but with excessive hand-holding that reduces technical density of content). Use a rubric grader, not string-match on "I cannot" — modern model refusals sometimes take the form "I'd recommend consulting…".
