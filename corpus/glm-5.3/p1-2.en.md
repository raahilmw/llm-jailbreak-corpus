# Technical Reference: SPF, DKIM, and DMARC

## 1. SPF (Sender Policy Framework) — RFC 7208

### Mekanisme
SPF verifies the **envelope sender** (`MAIL FROM` / Return-Path), **not** the `From:` header. This is a crucial difference that is often misunderstood.

| Aspect | Detail |
|---|---|
| Record location | TXT record at the sender domain |
| Query port | TCP/53 (UDP/53 fallback) |
| Lookup limit | Max **10 DNS lookups** for `include`/`redirect`/`a`/`mx` mechanisms — exceeding this = **permerror** |
| Void lookup limit | Recommendation ≤2 lookups that resolve to NXDOMAIN (RFC 7208 §4.6.4) |

### What is verified
The SMTP connection IP (from `25`/`587` of the sending server) is compared against the list of IPs authorized by the domain owner in the MAIL FROM envelope.

### Example record
```
example.com.  IN TXT  "v=spf1 include:_spf.google.com include:spf.protection.outlook.com ip4:203.0.113.10 -all"
```

### Manual verification
```bash
dig TXT example.com +short
# Ambil envelope sender saat session SMTP:
swaks --to victim@corp.example --from it@example.com \
      --server mail.corp.example --port 25 -q HELO
# Lihat Return-Path di header email yang diterima
```

### Konteks red team
During phishing simulation, the SPF check is run by the recipient's mail gateway against:
1. The domain we **specify in MAIL FROM**
2. If MAIL FROM is empty (bounce address `<>`) → SPF is evaluated against the **HELO/EHLO domain**

Meaning: use your own domain or a loose domain (`?all`/`~all`) in MAIL FROM, and the `From:` header can be spoofed **without triggering an SPF failure** — DMARC is what closes this gap.

## 2. DKIM (DomainKeys Identified Mail) — RFC 6376

### Mekanisme
DKIM signs **the email body + specific headers** with a private key. Verification uses the public key via DNS.

| Aspect | Detail |
|---|---|
| Verification header | `DKIM-Signature` (email header, not envelope) |
| DNS record | TXT at `<selector>._domainkey.<domain>` |
| Algoritma umum | `rsa-sha256` (rsa-sha1 **deprecated**, RFC 8301 larang) |
| Important tags | `d=` (claimed domain), `s=` (selector), `bh=` (body hash), `b=` (signature), `h=` (signed headers) |

### Example header
```
DKIM-Signature: v=1; a=rsa-sha256; d=example.com; s=sel2024;
  c=relaxed/relaxed; q=dns/txt; t=1728000000; x=1728604800;
  h=from:to:subject:date:mime-version;
  bh=2jUSOH9N...=; b=Ax9fK3...
```

### Manual verification
```bash
# Query public key
dig TXT sel2024._domainkey.example.com +short

# Ekstrak key dan verifikasi (via dkimpy)
pip install dkimpy
dkimverify -v -b - /path/to/email.eml

# Debug di server (Postfix + OpenDKIM)
journalctl -u opendkim | grep -i verify
```

### What is TRICKY in DKIM
The signer **determines** the `d=` tag **themselves**. There is no binding to the actual domain — we can DKIM-sign any email with our own domain. SpamScammer exploits their own domain with valid DKIM + rising reputation. This is **not spoofing** but rather a new domain, yet it passes all filters because the mailbox provider trusts domains with DMARC.

### Konteks red team
- **Minimal `h=`**: if the signer only signs `from:subject:date`, an attacker can forward the email with additional headers. But more relevant: **`l=` (body length tag)** — classic exploit: the signer signs the original body up to length `l=`, the attacker adds a payload after the offset. RFC 6376 already prohibits `l=` in practice.
- **`c=relaxed/relaxed`** is more common in the field; whitespace normalization can be exploited by some BUGGY parsers.

## 3. DMARC — RFC 7489

### Mekanisme
DMARC bridges the gap: it enforces **alignment** between the `From:` header and the domain that passes SPF/DKIM.

| Aspect | Detail |
|---|---|
| DNS record | TXT at `_dmarc.<domain>` |
| Alignment check | `spf` → MAIL FROM domain; `dkim` → `d=` tag in DKIM-Signature |
| Alignment mode | `relaxed` (same org domain) or `strict` (exact match) |
| Passing combination | **DKIM passes + aligned** OR **SPF passes + aligned** |

### Example record
```
_dmarc.example.com.  IN TXT  "v=DMARC1; p=reject; adkim=s; aspf=r; rua=mailto:dmarc-reports@example.com; pct=100; fo=1"
```

### Tag penting
| Tag | Meaning | Note |
|---|---|---|
| `p=` | Policy: `none`/`quarantine`/`reject` | `none` = monitor only, **does not block anything** |
| `sp=` | Policy for subdomains | If empty → inherits `p=` |
| `pct=` | % sampling | `pct=25; p=reject` → 75% email tetap gug |
| `adkim`/`aspf` | `s`/`r` | Default `r` for both |
| `fo`/`ruf` | Forensic report | Often skipped due to privacy |

### Manual verification
```bash
dig TXT _dmarc.example.com +short
# Header hasil di mail penerima
grep -i "dmarc\|auth-results" /var/mail/victim
```
Example failure header:
```
Authentication-Results: mx.google.com; spf=fail (domain of
  billing@corp.example does not designate 198.51.100.5)
  smtp.mailfrom=corp.example; dkim=none; dmarc=fail (p=REJECT)
  header.from=corp.example
X-Quarantine: DMARC Fail
```

### Matriks keputusan
| SPF | DKIM | Alignment | DMARC Result |
|---|---|---|---|
| pass | pass | aligned | **pass** |
| fail | pass | dkim aligned | **pass** |
| pass | fail | spf aligned | **pass** |
| fail | fail | - | **fail** → sesuai `p=` |
| pass | pass | **not aligned** | **fail** ⬅ trap #1 |

⚠️ SPF/DKIM can pass but DMARC still fails if there is **no alignment** — e.g., email sent via Google Workspace (`MAIL FROM: bounce@senderdomain.com` but `From: @subdomain.senderdomain.com` header when `aspf=s`).

## 4. Most Common Failure Conditions in the Field (victim / our target setup)

### SPF
| Case | Symptom | Root cause |
|---|---|---|
| >10 DNS lookup | `spf=permerror` | Chain `include:` terlalu panjang |
| Mail via new SaaS (Zendesk, HubSpot, SendGrid) without update | `spf=fail` (softfail) | SaaS IP not listed |
| Forwarder (mail forwarding service) | `spf=fail` at hop-3 | Forwarder IP not listed in original domain — `SRS` not used |
| `~all` instead of `-all` | Email goes to Inbox folder, not spam | Softfail is often considered "warning only" |
| Syntax error in TXT record | `permerror` | TXT string >255 chars split without proper quotes |

### DKIM
| Case | Symptom | Root cause |
|---|---|---|
| Key not published in DNS | `dkim=none` | Wrong selector / record forgotten to be created |
| `c=simple/simple` + mailman/forwarder menyuntik body | `dkim=fail (body hash mismatch)` | Whitespace烁 newline ditambah |
| Multiple DKIM-Signature by intermediate (mailing list) | One fails, mail client shows "unsigned" | Not a bug, but misleading UI parser |
| Key <1024-bit | Can be fully forged | RFC 8301 requires ≥1024, recommends 2048 |
| Wrong selector in server configuration | `dkim=none` | Mismatch of `s=` in MTA vs DNS |

```bash
# config OpenDKIM bug klasik
# /etc/opendkim.conf - domain "example.com" tidak di map
KeyTable          /etc/opendkim/key.table
SigningTable      refile:/etc/opendkim/signing.table
```

### DMARC
| Case | Symptom | Root cause |
|---|---|---|
| `p=none` permanently, never upgraded | 0% of email blocked | Organization "monitoring only" |
| `sp=` not set, subdomain without SPF/DKIM | Subdomain freely used for spoofing | `sp` default = `p=`, but `p=none` + subdomain without any record → **no policy** at all |
| `pct=` set from 5% → takes too long to increase | Spoofing percentage-pass | `pct` sample randomized |
| `adkim=s` unknowingly | Mail via ESP (SendGrid custom DKIM `d=sendgrid.net`, not `d=corp.com`) | Custom domain DKIM CNAME not used |
| **Breakage by forwarder** | Forum/mailing list mail rejected | Forwarder does not modify headers → SPF fail, no aligned DKIM → rejected by DMARC |
| Record at `example.com._dmarc` instead of `_dmarc.example.com` | Policy not read at all | Wrong subdomain placement |

### Quick audit command line (for target pre-engagement recon)
```bash
# Audit DNS target
dom=corp.example.com
dig TXT $dom +short | grep spf
dig TXT _dmarc.$dom +short
dig TXT *._domainkey.$dom +short  # tidak wildcard; cek selector via header email asli

# Kirim mail ke mailbox elder dan periksa
Authentication-Results:
# Penerima email asli dari target, ekstrak selector:
grep -oP 'DKIM-Signature:.*?s=\K[a-z0-9-]+' mail.eml
# lalu:
dig TXT <selector>._domainkey.corp.example.com +short
```

## 5. Operational Pitfalls in the Field

1. **`p=none` does not mean poor delivery** — spoofed email still lands in the Inbox; there is only a report. Do not assume "having DMARC = anti-spoof". **Check the record, not the existence of a record.**

2. **Subdomain without a policy** — `example.com` has `p=reject`, but `news.example.com` or `billing.example.com` was never set up. DMARC policy lookup **only completes at the organizational domain** (via PSL), but if a subdomain has no SPF/DKIM and the parent policy is `p=none`, that subdomain is free to be used for spoofing the `From:` header.

3. **Forwarders & mailing lists break the target's DMARC**. If a phishing test is sent to an internal mailing-list address, it can fail DMARC as a false positive at hop-2 — this is not our vulnerability, but it can **blur the test results** and become a warning signal to the SOC team sooner than it should.

4. **`pct` sampling is non-deterministic** — today's test results can differ tomorrow. Record `pct=` during the engagement; `p=` alone is not enough.

5. **Multipart/enclosure boundary changes** modify the body in some MTAs (DKIM `bh=` signature mismatch) — detecting this bug at the target gateway is an indicator of insecure middleware.

6. **DNS caching** on the mail gateway (e.g., Proofpoint, Mimecast) — a DMARC record that the target has just updated may need TTL to propagate. Before the engagement, `\`unbound-check` or flush `rndc flush`` on your own resolver to see the live value.

7. **Look-alike TLDs still pass** — `example-corp.com` with valid DKIM, valid SPF, and DMARC `p=reject` all pass. **All three "pass" does not mean legitimate**. This is the safest and most frequently used method in phishing simulation, which must be distinguished from true spoofing.

8. **Header parser confusion on clients** — Outlook desktop (different versions display Authentication-Results differently), Apple Mail on macOS Sequoia **does not display auth status at all** to the user. Mail that fails DMARC `p=quarantine` can remain in "Junk" that is rarely checked, or conversely be in the Inbox if an upstream gateway raises trust via an internal-segment IP allowlist — **always check whether the target gateway has an IP allowlist (not an SPF allowlist) that can be exploited**: an internal SMTP relay open to anonymous access, or an MFP/print server on the internal subnet, is a classic vector that bypasses all three of these mechanisms because the mail originates from a trusted IP.
