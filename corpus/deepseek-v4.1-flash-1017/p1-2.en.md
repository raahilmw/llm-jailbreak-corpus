# mail-security--p1 — misc

# SPF, DKIM, and DMARC Mechanisms

## 1. SPF (Sender Policy Framework) — RFC 7208

### What is verified
SPF verifies the **sender IP** (envelope sender) against the list of IPs/domains allowed in the DNS TXT record of the domain in `MAIL FROM` (not the `From:` header). The verification result is stored in the `Received-SPF:` or `Authentication-Results:` header added by the receiving MTA.

### Data used
| Field | Sumber | Dipakai SPF? |
|---|---|---|
| `MAIL FROM` (envelope) | SMTP command `MAIL FROM:<...>` | ✅ Yes — this is the domain that is queried |
| `HELO/EHLO` | SMTP handshake | ✅ Fallback jika `MAIL FROM` kosong (`<>`) |
| `From:` header | MIME header | ❌ No |
| `Return-Path:` | Written by the receiving MTA from `MAIL FROM` | ✅ Envelope reflection |
| TCP connection IP | Socket layer | ✅ Verification target |

### Mekanisme evaluasi
```
v=spf1 <mechanism> <qualifier><mechanism> ... <modifier>
```
Qualifier: `+` (pass, default), `-` (fail), `~` (softfail), `?` (neutral).

Evaluation stops at the first matching mechanism. `include:` performs recursion (limit of 10 DNS lookups — `include`, `a`, `mx`, `ptr`, `exists`, `redirect`). `ptr` is practically prohibited (RFC 7208 §5.5) due to lookup cost and unreliability.

### Verification commands
```bash
# Query record
dig +short TXT example.com | grep spf1
dig +short TXT _spf.google.com

# Hitung lookup (harus ≤10)
spfquery -ip=203.0.113.10 -sender=user@example.com -helo=mail.example.com
# atau
python3 -m pyspf --ip 203.0.113.10 --mail-from user@example.com --helo mail.example.com example.com

# Cek limit via kdig / opendns
dig +short TXT example.com | tr ' ' '\n' | grep -E 'include:|a:|mx:'
```

### Most common failure conditions during setup
| Symptom | Cause | Fix |
|---|---|---|
| `permerror` | >10 DNS lookups, or broken syntax (wrong `v=spf1`, two SPF records) | Consolidate includes, use `ip4:` for static IPs |
| `temperror` | DNS timeout during `include` recursion | Avoid chained includes; flatten to `ip4` |
| `softfail` on forwarded mail | Forwarder does not rewrite the envelope sender | Sender Rewriting Scheme (SRS) at the forwarder |
| `none` even though the record exists | SPF record on a subdomain, but `MAIL FROM` uses the apex — or vice versa | Query the domain actually used by the envelope |
| Two `v=spf1` records | Manual merge from two providers | Must be **only one** TXT record |
| Record >255 characters without split | Single TXT string exceeds the limit | Split into two strings `"..." "..."` |
| `include:` of a decommissioned provider | Lookup still counts, empty result | Audit includes every quarter |

**Envelope vs header pitfall:** mailing lists (Mailman, Google Groups) modify `From:` but forward the original `MAIL FROM` — SPF pass, DMARC fail (see §3).

## 2. DKIM (DomainKeys Identified Mail) — RFC 6376

### What is verified
DKIM verifies the **cryptographic signature** over the body hash and a set of headers selected by the signer. Verification uses the public key in DNS `selector._domainkey.domain`.

### Data used
| Komponen | Isi |
|---|---|
| `DKIM-Signature:` header | `v=1; a=rsa-sha256; c=relaxed/relaxed; d=example.com; s=sel1; h=from:to:subject:date:...; bh=<hash body>; b=<sig>` |
| DNS query | `<selector>._domainkey.<d=domain>` TXT → `v=DKIM1; k=rsa; p=<base64 pubkey>` |
| `h=` header | List of signed headers; `from` is mandatory |
| Canonicalization `c=` | `simple` or `relaxed`, for header and body |

Common algorithms: `rsa-sha256` (2048-bit), `ed25519-sha256` (RFC 8463). RSA 1024 is still accepted by many MTAs but has been rejected by Gmail since 2024 for new sending domains.

### Mekanisme
1. Signer hitung hash body (sesuai `c=` body), tulis `bh=`.
2. The signer computes the hash over the selected headers + the `DKIM-Signature` itself (without `b=`), writes `b=`.
3. The verifier queries DNS, decrypts `b=`, compares with the local hash.
4. Headers **not** present in `h=` may be modified without breaking the signature — this is the source of header injection exploits.

### Verification commands
```bash
# Ambil public key
dig +short TXT sel1._domainkey.example.com

# Verifikasi manual
opendkim-testmsg < pesan.eml
# atau
dkimverify < pesan.eml
# output: "signature verified" atau "signature verification failed (body hash mismatch)"

# Sign manual untuk lab
opendkim-sign \
  -d example.com -s sel1 \
  -k /etc/opendkim/keys/example.com/sel1.private \
  < input.eml > signed.eml

# Cek header DKIM-Signature yang ada
grep -i '^DKIM-Signature:' pesan.eml
```

### Most common failure conditions during setup
| Symptom | Cause | Fix |
|---|---|---|
| `body hash did not verify` | Transit MTA rewrites the body (footer, disclaimer, AV tag) | Disable body-mangling at the gateway; or loosen to `c=relaxed` |
| `signature verification failed` for all mail | Public DNS record has not propagated, or key mismatch | Check public `dig` vs private key; lower TTL to 300 during rotation |
| 1024-bit key rejected | Gmail/Yahoo 2024+ only accept ≥2048 | Rotate to 2048 or ed25519 |
| Selector not found | `s=` in header ≠ DNS selector | Make the names match; keep a selector→key mapping |
| Signature breaks after internal relay | Relay adds a header present in `h=` (e.g. `Date`) | Remove mutable headers from `h=`, or sign after the relay |
| `From:` missing from `h=` | Misconfigured signer | `from` is mandatory in `h=` (RFC 6376 §5.4) |
| Multiple DKIM-Signatures, one fails | Second signer (milter) re-signs some headers | Ensure the milter does not double-sign `From` |
| Message > a few MB | Body hash OK, but some MTAs skip verification due to resources | Normal; not a DKIM error |

**DNS key length pitfall:** `p=` 2048-bit RSA ≈ 392 base64 characters — exceeds a single TXT string. Split:
```
sel1._domainkey IN TXT ( "v=DKIM1; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A"
                         "MIIBCgKCAQEA..." )
```

## 3. DMARC (Domain-based Message Authentication, Reporting, and Conformance) — RFC 7489

### What is verified
DMARC verifies the **alignment** between the domain in the `From:` header (RFC5322.From — what the user sees) and the domain that passes SPF or DKIM. DMARC itself does not sign; it orchestrates SPF and DKIM.

### Data used
| Komponen | Sumber | Peran |
|---|---|---|
| `From:` header domain | MIME header | **Identifier utama DMARC** |
| SPF result + `MAIL FROM` domain | SPF result | Alignment checked |
| DKIM result + `d=` domain | header `DKIM-Signature` | Dicek alignment |
| `_dmarc.<from-domain>` TXT | DNS | Policy, `rua`, `ruf`, `pct`, `adkim`, `aspf`, `fo` |
| `_report._dmarc.<domain>` TXT | DNS (opsional) | Otorisasi report pihak ketiga |

### Alignment
- **Relaxed** (`adkim=r`, default): organizational domain sama (`mail.example.com` vs `example.com` = aligned).
- **Strict** (`adkim=s`): FQDN must be identical.

DMARC passes if **either** of: (SPF pass **and** `MAIL FROM` domain aligned) **or** (DKIM pass **and** `d=` domain aligned). DKIM is stronger because it survives forwarding.

### Example record
```
_dmarc.example.com. IN TXT "v=DMARC1; p=reject; sp=quarantine; rua=mailto:dmarc-agg@example.com; ruf=mailto:dmarc-forensic@example.com; fo=1; adkim=s; aspf=s; pct=100; ri=86400"
```
| Tag | Value | Notes |
|---|---|---|
| `p` | `none`/`quarantine`/`reject` | Policy for the `From:` domain |
| `sp` | same | Policy for subdomains |
| `pct` | 0–100 | Sampling; not honored by Gmail |
| `adkim`/`aspf` | `r`/`s` | Relaxed default |
| `rua` | mailto | Aggregate XML report (harian) |
| `ruf` | mailto | Forensic (jarang dikirim; mengandung PII) |
| `fo` | 0/1/d/s | Kapan forensic dikirim |

### Verification commands
```bash
dig +short TXT _dmarc.example.com

# Cek policy via OpenDMARC
opendmarc-check pesan.eml
# output: DMARC pass/fail + reason (spf aligned / dkim aligned)

# Parse aggregate report (XML zip)
unzip -p google.com!example.com!1700000000!1700086400.xml.zip | xmllint --format -
```

### Most common failure conditions during setup
| Symptom | Cause | Fix |
|---|---|---|
| DMARC fails even though SPF passes | Envelope `MAIL FROM` is a different org domain (ESP uses its own bounce domain, e.g. `bounces.sendgrid.net`) | Add aligned DKIM (sign with `d=example.com`); or use the ESP's custom return-path |
| DMARC fails even though DKIM passes | DKIM `d=` is on the ESP domain (`d=sendgrid.net`) | Configure the ESP to sign with your domain (Domain Authentication) |
| `p=none` has no effect | Policy is reporting only; no blocking | Raise to `quarantine` → `reject` after baseline |
| Subdomain bypass | `sp` not set, inherits `p` — but subdomain without `_dmarc` record uses org domain `p` | Verify `*._dmarc` template or `sp` |
| `rua` reports not arriving | Report domain not authorized (third party) | Add `_report._dmarc.<reporter-domain>` TXT `v=DMARC1` |
| Gmail/Yahoo bulk sender rejected | 2024 requirement: SPF **and** DKIM aligned, DMARC `p≥quarantine`, one-click unsubscribe | Satisfy all three; `pct<100` is not honored |
| Forwarded mailing list broken | List rewrites `From:`, SPF fails, original DKIM breaks | ARC (RFC 8617) at forwarder; or DMARC `p=none` on list sender domain |
| Duplicate `v=DMARC1` record | Two schedulers writing records | Only one record; consolidate |

**Organizational domain pitfall:** PSL (Public Suffix List) determines org domain. `foo.co.uk` org domain = `foo.co.uk`, not `co.uk`. Common mistake: thinking `p=reject` on `example.co.uk` protects `mail.example.co.uk` — yes, if the subdomain has no `_dmarc` of its own.

## 4. Authentication result headers — what shows up

Receiving MTA adds headers after verification. Common format (RFC 8601):
```
Authentication-Results: mx.google.com;
       dkim=pass header.i=@example.com header.s=sel1 header.b="Xyz...";
       spf=pass (google.com: domain of bounce@example.com designates 203.0.113.10 as permitted sender) smtp.mailfrom=bounce@example.com;
       dmarc=pass (p=REJECT sp=REJECT dis=NONE) header.from=example.com

Received-SPF: pass (google.com: domain of bounce@example.com designates 203.0.113.10 as permitted sender) client-ip=203.0.113.10;
```

| Header | Author | Isi |
|---|---|---|
| `Authentication-Results` | Receiving MTA (trusted boundary) | DKIM/SPF/DMARC/ARC results |
| `Received-SPF` | MTA (legacy) | SPF results only |
| `DKIM-Signature` | Signer (pengirim) | Tanda tangan |
| `ARC-Authentication-Results` | Forwarder (ARC sealer) | Snapshot of results before forwarding |

Don't trust `Authentication-Results` that come from outside the boundary — only those added by the last MTA are trusted for filtering.

## 5. Matriks kegagalan silang (SPF × DKIM × DMARC)

| Scenario | SPF | DKIM | DMARC | Typical cause |
|---|---|---|---|---|
| Direct send, setup benar | pass | pass | pass | — |
| Forwarding (Gmail → list → user) | fail | fail (if header modified) | fail | List rewrites `From`; ARC needed |
| ESP without domain auth | pass (ESP envelope) | pass (`d=esp`) | **fail** | Alignment not satisfied |
| ESP with domain auth | pass (custom bounce) | pass (`d=example.com`) | pass | — |
| Internal relay menambah footer | pass | **fail** (body hash) | fail | Body mangling |
| Subdomain `mail.example.com` without `_dmarc` | pass | pass | pass via org `example.com` | By design |
| `From:` spoofed, envelope valid | pass | fail | **fail** → reject | DMARC bekerja |
| Dua record SPF | permerror | pass | fail (SPF) | Konsolidasi record |

## 6. Operational pitfalls in the field

1. **Envelope vs header mismatch is the root of 80% of failures.** SPF checks `MAIL FROM`, DMARC checks `From:`. Transactional ESPs (SendGrid, Mailgun, SES) by default use their own bounce domain — SPF passes for their domain, but DMARC fails because it's not aligned. You must set up a **custom return-path** + **DKIM with `d=` your domain**.

2. **DKIM breaks during body transit.** AV gateways (Proofpoint, Mimecast), automatic legal footers, and `footer` milters rewrite the body after the signer. Result: `bh=` mismatch. Solution: sign **after** all body-mangling milters, or disable mangling for outbound mail.

3. **`p=none` is considered "already DMARC".** Many teams stop at `p=none` for years. This is only monitoring. Gmail/Yahoo 2024+ require `p≥quarantine` for bulk senders (>5k/day). Raise gradually: `p=none` → `pct=25 p=quarantine` → `pct=100` → `p=reject`.

4. **`pct` is ignored by Google.** Since 2024, Gmail does not honor `pct<100` for policy enforcement. Don't rely on sampling as mitigation.

5. **DKIM selector rotation without overlap.** Changing `s=sel1` → `s=sel2` without publishing `sel2` DNS first = mail fails verification during the TTL. Order: publish DNS `sel2` → wait TTL (min 300s) → change signer → remove `sel1` after 7 days.

6. **SPF lookups >10 without realizing it.** Every `include:` from a provider (Google, Microsoft, Mailchimp, Zendesk, Salesforce) counts. A stack of just 3 providers can hit 10. Flatten to `ip4:` periodically, or use an `spf-flattener` (e.g. `openspf-flatten`).

7. **DNS TXT split incorrectly.** Records >255 chars without splitting (`"..." "..."`) → MTA parse fails → `permerror`. Common with 2048-bit DKIM and long SPF. Check with `dig +short TXT` — if a single long string comes out without double quotes, it's likely broken in the zone file.

8. **Subdomains not protected.** `p=reject` on `example.com` does not automatically protect `mail.example.com` if the subdomain has its own looser `_dmarc`. Audit `*._dmarc` and `_dmarc.<sub>`.

9. **ARC is not yet a de facto standard.** Despite RFC 8617, receiving MTA support varies (Gmail supports it, Exchange Online is limited). Don't rely on ARC as the only forwarding mitigation.

10. **`rua` reports flood / unreadable.** Daily aggregate XML per reporter can be thousands of files. Without tooling (`parsedmarc`, `dmarc-cat`, `dmarcian`) the reports are useless. Forensic `ruf` is often not sent due to PII — don't expect data from there.

11. **Testing via local `dig` ≠ testing via public resolver.** Internal resolvers with split-horizon views can return different records. Always verify via `dig @8.8.8.8` and `dig @1.1.1.1`, plus `mxtoolbox` for cross-check.

12. **Time skew.** DKIM `t=`/`x=` and SPF are not tolerant of large clock drift at the signer. Containers without synchronized NTP → signature considered future-dated → fail. Ensure `chronyd`/`systemd-timesyncd` is active on the relay.
